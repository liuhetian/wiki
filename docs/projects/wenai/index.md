# wenai：把角色陪伴的连续性写进文件

wenai 属于 AI 角色扮演（AI role-playing）与陪伴式 Agent（companion agent）。最简单的起点是给模型一段人格 prompt，接着一直聊天。它在这个起点上增加了会话恢复、分类档案、发送后写回、统计口径和生图约定：**重要状态留在文件里，每轮按需读回，互动结束后再更新**。执行主体仍然是宿主 Agent，仓库主要用自然语言规定流程。

下面按功能展开，用一次“在咖啡馆参加读书会，接着去散步”的日常场景贯穿示例。上游实际围绕成人互动设计，本文过滤了露骨内容；**标为“示例”的 prompt、档案字段和记忆格式都是本文构造或改写的，不是上游提供的通用陪伴模板**。来源和原文定位见[维护记录](../../maintenance/projects/wenai.md#sources)。

## 人格、会话规则、工具分别放在哪里

只在人格 prompt 里写“你喜欢读书，记住我们的约定”，模型可能接得住眼前几轮，却没有规定约定存在哪里、哪一刻保存、重启后读什么。wenai 补的是这些执行约定。README 明确说不含人格设定，角色性格、语气要放在宿主的 SOUL.md 或其他 system prompt 里。

理解这个分工，才能看懂仓库为什么小。它只有八个文件：README、主 skill、工作流说明、四份档案模板和一个 ComfyUI JSON。人格材料、聊天界面、文件工具、消息通道和模型服务由外面提供；每日记忆是运行时要写出的文件，初始仓库里没有现成的聊天历史。

| 层 | 这层放什么 | 谁提供 |
|---|---|---|
| 人格 | 性格、语气、身份背景 | 使用者与宿主 |
| 主 skill | 何时读档案、生成回复后做什么、失败如何补记 | wenai 的 `SKILL.md` |
| 持久状态 | 用户偏好、角色状态、累计统计、每日场景记忆 | 模板由上游提供，内容由运行时更新 |
| 工具 | 读写文件、生成图片、发送消息 | 宿主及外部服务 |

这个项目值得看的地方，是把“记住我”拆成明确的读写责任。它没有提供独立运行的聊天后端，也没有程序在每一步替 Agent 验证执行结果。

## 功能一：把一段大 prompt 分成有时机的规则

人格 prompt 通常强调“怎么说话”。wenai 的主文件还规定“开始会话、互动中、发送后、压缩前分别做什么”。对应上游 `SKILL.md:18–53`、`112–122`，入口恢复、回复与生图、写回、场景线、日常联动是不同区块。

过滤成日常陪伴题材后，这类 prompt 大致长成下面这样。它保留原项目的流程分块，但删掉了成人场景指令，改写了档案名称；不能将它当作原文逐字存档。

```text title="本文改写：会话规则的骨架"
--8<-- "projects/wenai/assets/examples/prompt.txt"
```

这里的数据结构首先是 Markdown 的结构：二级标题划阶段，列表规定前后顺序，文件路径指向外部状态。它没有对应的 Python 类或 JSON Schema，也没有解析器强制检查某个标题必须存在。模型读懂这些自然语言，再决定调用哪些宿主工具。

拆出时机的意义可以用一个失败案例说明：如果模型先说“我记住了”，随后结束回复，没有执行文件写入，下一次重启仍然会丢。原项目用发送图片后的明确约束，把保存挂在一次具体动作之后。约束更清楚，但是否真的执行，仍取决于 Agent。

## 功能二：档案按职责拆开，避免把所有记忆混成聊天摘要

“用户喜欢什么”“角色现在处于什么状态”“过去发生过多少次”是三类问题。一份不断追加的聊天摘要可以混着记录，却不容易判断这一轮该看哪一段、哪一条需要覆盖更新。wenai 用几份小文件分开承担这些职责。

上游四份模板有明确的成人主题，本文只说明其结构。`assets/fetishes.md` 是偏好强度清单，初始基本为空；`assets/sensitivity.md` 是含程度、首次日期、反应等列的表格；`assets/profile.md` 用小节和字段保存角色身体状态；`assets/stats.md` 用短行保存累计数。对应更新规则在 `SKILL.md:55–110`。

换成读书会的日常题材，可以直观看到它们的结构差别。下面的文件名、条目和数值全部是演示数据，尤其活动累计的分类不能视为上游统计口径。

```text title="本文构造：四类档案的结构示意"
--8<-- "projects/wenai/assets/examples/profiles.txt"
```

偏好是相对长期的；状态描述“现在”；反应记录保留第一次发生的日期；统计只回答总量。它们有不同的更新方式：发现新偏好时追加或调级，状态改变时覆盖当前值，发生新事件时更新累计量。原项目还要求把偏好要点定期同步到 MEMORY.md，但没有提供负责定时执行的调度器。

上游要求互动轮次重读三份场景档案，统计文件只在计数或补记时读取。这让新一轮能看到磁盘上的最新值，代价是多次文件读取和上下文开销。模板没有程序级类型检查；星级、日期、总数能否保持一致，靠模型和宿主共同维持。

## 功能三：每日记忆保存“停在哪里”，新会话从那里接

分类档案能告诉模型“这个人喜欢热茶”，但未必告诉它“刚讨论完第三章，出门前要收好书签”。这类短期进度需要另一种载体。wenai 指向 `memory/YYYY-MM-DD.md`，用每日文件保存场景线、序号、消息标识和计数变化。

上游 `SKILL.md:115` 的原文很直接：

```text title="上游原文：新会话恢复要求"
--8<-- "projects/wenai/assets/examples/upstream-memory-rule.txt"
```

但它没有随仓库交付每日记忆模板，也没有限定字段顺序。下面是依据其要求构造的一份文件，补了便于阅读的标题与标签。messageId 和序号都是演示值。

```text title="本文构造：memory/YYYY-MM-DD.md 可以长什么样"
--8<-- "projects/wenai/assets/examples/memory.txt"
```

读这份文件，模型才知道本轮的“继续”指向散步，书签仍是未完成事项，下一张图片要接 00008。长期偏好可以同时存在于档案里；每日记忆的重心是恢复进度，而不必重新复制全部人格与偏好。

这里有一个重要边界：**文件在磁盘上，不代表它已经进入模型上下文**。宿主必须真的读取它，并把读取结果提供给模型。上游通过 prompt 要求 Agent 自己去做，没有实现检索器，也没有定义“最近”究竟扫描几天、遇到多个场景如何选择、文件过长时如何裁剪。

### 新会话读回文件，实际会有什么区别

用读书会场景做了一次 DeepSeek 对照：首轮让模型生成记忆，由本文脚本写入磁盘；之后分别发起两个全新的请求，两者都没有首轮聊天历史。其中一个没有记忆，另一个由脚本读回刚才的文件后提供给模型。两组统一要求只按已知记录回答，缺少过去事实时问清，不允许编造。

两组都问：“接着上次的安排吧。我们下一步做什么，出门前还要做什么？我喝什么，下一张图用哪个序号？”下面保留真实返回，不用手写对话冒充效果。

```text title="真实返回：没有提供记忆的新会话"
--8<-- "projects/wenai/assets/experiment/out/02-no-memory.reply.txt"
```


无记忆组要求用户补充安排；带记忆组恢复了散步、蓝色书签、不加糖的热茶以及 00008。并不是两个不同人格表现不同，差别在于这一轮实际拿到了哪些事实。缺资料时先问清，也是实验统一提供的约束，不能归功于上游的某个程序检查。

## 功能四：发送后再写回，把场景进度和消息对应起来

场景连续性也发生在输出端。假设生成了一张图片，却不知道有没有成功发出：下一轮可能把没发出的内容当成已发生，也可能重复发送已经成功的结果。wenai 要求用消息工具明确投递，再完成统计和每日记忆写入，记忆里保存 messageId、当前序号和下一张序号。

对应 `SKILL.md:43–53`，主线是发送、更新统计、写每日记录；偏好、反应和角色状态在发生变化时再更新。序号表示“这张是第几张”，messageId 对应外部聊天通道中的消息。两者各有职责，记下它们便于后续对照当前进度。

本文用一份故障状态说明“补记”在处理什么。它只是示意，并不是上游实际提供的待办队列或事务日志。

```text title="本文构造：消息成功但文件写入失败的中间状态"
--8<-- "projects/wenai/assets/examples/ledger.txt"
```

上游要求补记前先读实际文件，失败项要在后续优先补齐。这样至少避免模型凭旧上下文假设某个值仍未更新。但如果统计已经写成功、每日记录没成功，累计数本身不能证明某次事件是否计入，重复加一仍有风险。

这里的亮点是明确承认一轮会话可能只完成了一半，并规定恢复时先核对落盘事实。它没有程序层面的事务、事件唯一键约束或自动重试队列，不能把这段 prompt 等同于数据库事务保证。

## 功能五：先定义一次事件，再累计数字

让模型“每次更新统计”仍然太笼统。一个活动连续聊了五轮，可能被算成五次；模型换一种描述，也可能把同一事件当成新事件。wenai 的统计段落区分新事件、延续动作和独立维度。本文过滤具体成人分类，只讨论这种口径设计。

用日常活动举例：一次读书会里继续讨论第三章，不能因为收到一次“继续”就新增一次读书会；结束后另开一次活动，才是新事件。这是帮助理解的替换案例，并不意味着上游已经实现了 `reading_sessions` 的规则。

对应的数据结构很轻：一个文件保存几个累计键和值，更新规则则放在主 skill。文件负责保留结果，prompt 负责解释何时加一。这个分工让文件短、容易读，却把事件识别交给了模型。

累计数与每日增量也有不同用途。累计数回答“总共多少”，每日记忆里的增量回答“今天这一轮变了什么”。后者能辅助核对；若要更有把握地防止重复累计，还需要记录事件身份、处理状态并由程序强制检查，这些实现不在原仓库里。

## 功能六：压缩边界先补缺，再写快照

长对话会遇到上下文压缩。只写一段“我们今天聊得很开心”的摘要，可能丢掉下一张序号、未完成约定或未写成功的变更。wenai 在 `SKILL.md:51–53` 把压缩前的 flush 当作明确时机：先检查还没完成的落盘，再写场景快照。

这个顺序有意义。若统计还未写成，就先把旧值当成最终快照，重启后的 Agent 会在看似完整、实际过期的状态上继续。先核对失败项，再保存场景线和计数变化，能让交接材料更接近磁盘事实。

但“检查所有未完成项”仍然是自然语言要求。仓库没有持久的未完成操作集合，也没有压缩回调的程序实现；宿主是否有 flush 机会、压缩是否突然发生，都在它的控制范围之外。示例记忆中“待补记：无”是本文加的解释字段，上游没有规定必须使用这行。

## 功能七：把角色外观、场景和生图环境分开

如果每轮随意重写角色外观，生成图片可能各像各的人。wenai 要求使用者初始化固定角色特征，每轮再结合当前场景组织图片输入；具体生成交给外部 ComfyUI。固定外观提供连续的描述约束，但不能保证生成结果完全一致。

从分工看，这条线包括：宿主接收生图调用，工作流加载模型和相关组件，生成图片后由消息工具投递，最后把结果对应的序号与消息标识写回记忆。仓库附带的 JSON 是生图图结构，没有实现聊天会话循环、文件记忆或消息通道。

本文不展开露骨标签、完整生图配方和部署参数，也没有生成图片。需要看到的取舍是：上游要求为速度直接发送、不做识图校验。因此有固定外观规则，不等于运行时有外观一致性验证；失败图如何拦截，也没有独立检查器。

图片链路与文本记忆可以分别讨论。上面的实测只用了文本模型和文件，没有 ComfyUI、LoRA、聊天账号或图片发送工具；读回一份记忆成功，不能顺带证明图片生成和投递可用。

## 功能八：日常提醒和看板复用同一份状态

上游还有日常问候、约定跟进和查询统计的要求，位置在 `SKILL.md:118–122`。这些入口复用前面的状态：问候延续已有场景，跟进从记忆里的约定取线索，统计查询读取累计数据。这样日常消息与场景互动不必各维护一套互不相通的记录。

用读书会场景类比，用户下次来问“我们还欠什么安排”，有未完成约定的文件才可能回答“先收好书签，再去散步”。这是本文的解释性例子，上游没有这条读书会功能，也没有待办管理器。

“主动提醒”尤其要区分两件事：prompt 可以要求模型在被唤醒时检查约定；真正到时主动运行，还需要宿主的调度和消息通道。仓库没有 cron 配置或提醒服务。数据看板同样只是要求按需输出统计和活跃日期，没有附带可视化网页。

## 谁管什么，以及能从这个项目拿走什么

| 责任 | 上游规定了什么 | 没有由它保证的部分 |
|---|---|---|
| 使用者 | 填写称呼、账号与角色外观 | 真实身份认证、人格完整性 |
| 模型 | 理解场景、识别事件、决定档案变化 | 计数准确、每条规则都执行 |
| 宿主 | 提供文件、消息、生图等工具 | 仓库没有包含宿主实现 |
| 文件 | 保存当前状态、累计量和接续线索 | 类型校验、事务、冲突合并 |
| 外部生图环境 | 按工作流执行模型图 | 图片质量与角色一致性 |

账号限制也属于这个边界：把允许的账号写在 prompt 中，是要求 Agent 拒绝其他调用；真正可靠的访问控制，需要宿主验证消息来源。原仓库没有这样的认证代码，不能把占位符填写步骤当成权限系统。

可以借鉴的是几种具体安排：人格和流程分开放；长期档案和短期进度分开存；在回复之外明确写回时机；给失败补记与压缩快照留位置；累计之前先定义事件口径。这些安排能让一次临时聊天有更清楚的状态交接方式。

自然语言规约依赖 Agent 遵守。要用于更重要的数据或多人并发场景，还需要独立设计持久化、鉴权与去重实现，不能把本文的展示脚本或过滤示例当作上游已有的工程能力。
