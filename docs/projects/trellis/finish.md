# 收尾与沉淀：检查、写回规范、分组提交、记日志

裸用时，模型改完代码就说「完成了」；这次踩到的坑只留在对话里，一压缩、一关窗口就没了，下次照样踩。提交的时候，它还可能把用户手边没提交的改动一起打包进去。Trellis 的阶段 3 把收尾拆成几步：检查、写回 spec、按组提交、归档加记日志，另给一个翻旧会话的工具。这些步骤绝大部分是 skill 和命令的文字，程序只管归档和写日志的格式。本篇只读了源码，没有实跑，每节贴源码模版和文字的中译；模版路径省略前缀 `packages/cli/src/templates/`。

这几样各在什么时候进上下文：

| 什么 | 什么时候进上下文 | 谁决定 |
|---|---|---|
| `trellis-check` | 每轮提醒的流程里点名；描述写「代码写完需要验证、提交前、长会话里抓上下文漂移时用」 | 模型 |
| `trellis-update-spec` | 阶段 3.3，必做一次；描述写「从调试、实现、讨论里学到值得留给以后会话的东西时用」 | 模型 |
| `trellis-break-loop` | 阶段 3.2，按需；描述写「修完 bug 之后用，防止同一类 bug」 | 模型 |
| 阶段 3.4 提交 | 模型跑 `get_context.py --mode phase --step 3.4` 时拉到 | 模型 |
| `/trellis:finish-work` | 用户输入；3.5 只提醒用户可以输入 | 用户 |
| `trellis-session-insight` | 描述里列了「上次怎么解的」「之前讨论过吗」这类原话 | 模型 |

**功能**：阶段 3.3 是必做一次的步骤，结论是「没什么要写」也得走一遍判断：

```text title="译文 · code-spec 优先规则"
## code-spec 优先规则（关键）

在这个项目里，实现工作说的「spec」指的是 **code-spec**：
- 能执行的契约（不是只讲原则的文字）
- 具体的签名、载荷字段、环境变量名和边界行为
- 能测试的校验 / 错误行为

改动碰到基础设施或跨层契约时，必须写到 code-spec 的深度。

### 强制触发条件

改动包含下面任何一项，就要写到 code-spec 深度：
- 新增 / 改动命令或 API 签名
- 跨层的请求 / 响应契约变了
- 数据库 schema / 迁移变了
- 基础设施集成（存储、队列、缓存、密钥、环境变量接线）

### 必须产出（7 节）

触发了的任务，下面各节都要写：
1. 范围 / 触发条件
2. 签名（命令 / API / 数据库）
3. 契约（请求 / 响应 / 环境变量）
4. 校验与错误矩阵
5. 正常 / 基础 / 错误三类用例
6. 必须有的测试（带断言点）
7. 错误写法 vs 正确写法（至少一对）
```

skill 后面还按收获的类型给了模版：设计决定、项目约定、新模式、禁用模式、常见错误、坑。和 `guides/` 下的「思考清单」分开放：编码规范进各层目录，「做 Y 之前别忘了查 X」这类提醒进 `guides/`。

## 同一个 bug 修了好几次，复盘一次 { #break-loop }

**问题**：导出的金额第一次是浮点误差，第二次是千分位逗号把 CSV 列切坏了，第三次才发现根子在金额字段没统一格式化（构造情境）。修好了，但下次换个字段还会这样。

**功能**：阶段 3.2 按需：同一个问题修了不止一次，就加载 `trellis-break-loop`，从五个维度分析：

```text title="译文 · break-loop 开头（后三维摘要）"
# 打破循环 —— 深度 bug 分析

调试结束后用这个做深度分析，打破「修 bug -> 忘掉 -> 再犯」的循环。

## 分析框架

从这 5 个维度分析刚修好的 bug：

### 1. 根因类别
| 类别 | 特征 | 例子 |
| A. 缺 spec | 没有文档说该怎么做 | 新功能没有检查清单 |
| B. 跨层契约 | 层与层之间的接口不清 | API 返回的格式和预期不同 |
| C. 改动没传播到位 | 改了一处，漏了别处 | 改了函数签名，漏了调用点 |
| D. 测试覆盖缺口 | 单测过了，集成挂了 | 单独能跑，合起来就坏 |
| E. 隐含假设 | 代码依赖没写下来的假设 | 时间戳是秒还是毫秒 |

### 2. 之前的修法为什么失败（如适用）
- 表面修复：修了症状，没修根因
- 范围不全：找到了根因，没覆盖所有情况
- 工具局限：grep 漏了，类型检查不够严
- 思维定式：一直在同一层找，没想到跨层

（3. 防范机制：文档、架构、编译期、运行时、测试、代码评审六类；4. 系统性扩展：别处有没有同类问题；5. 知识沉淀：更新 guides 和 spec、建 issue。）
```

后半段另附一套贝叶斯推理的思考框架：先列先验、看证据、更新信念、找能区分假设的证据、说明置信度。

## 提交分两组：本会话改的、不认识的 { #commit }

**问题**：工作区里有用户自己在另一个窗口改了一半的文件。模型 `git add -A` 一把提交，用户的半成品混进了「feat: 订单导出 CSV」。

**功能**：阶段 3.4 让模型先看脏文件、学最近的提交风格，再把文件分成两组，给出一份提交计划，一次确认：

```markdown title="模版 · trellis/workflow.md:600-650"
--8<-- "projects/trellis/assets/trellis-src/packages/cli/src/templates/trellis/workflow.md:600:650"
```

```text title="译文 · 3.4 的要点"
**spec 同步引导**：起草提交之前先问：这个任务是不是修了 bug，或者发现了不显然的知识，应该写进 `.trellis/spec/`，免得以后的你（或以后的 AI）再犯？是，就先回到 3.3 —— spec 的改动属于这个任务的同一批提交，不是被遗忘的后续。

由 AI 主导把这个任务的代码改动分批提交，好让之后的 `/finish-work` 干净地跑完。目标：先出工作提交，然后才是记账的提交（归档 + 日志）—— 两者绝不交错。

1. 看脏状态：`git status --porcelain`，记下每个脏路径。工作区干净就跳到 3.5。
2. 从最近的历史学提交风格：`git log --oneline -5`，留意前缀约定（feat: / fix: / chore: / docs: ……）、语言（中文 / 英文）和长短。
3. 把脏文件分成两组：
   - 本会话 AI 改的 —— 这个会话里你通过 Edit / Write / Bash 写过或改过的文件。你知道改了什么、为什么改。
   - 不认识的 —— 这个会话里你没碰过的脏文件（可能是用户手改的、上个会话留下的半成品，或者无关的工作）。不要悄悄把它们带进去。
4. 起草提交计划。把 AI 改的文件按逻辑分成几个提交（一个连贯的改动单元一个提交，不是一个文件一个提交）。不认识的文件单独列在最下面。
5. 一次性给出计划，请求一次确认，格式：
   拟提交（按顺序）：
     1. <提交信息>
        - <文件>
   不认识的脏文件（不在任何提交里 —— 请确认要不要带上）：
     - <文件>
   回复 'ok' / '行' 就执行。回复修改意见，或回复 '我自己来' / 'manual' 取消。
6. 确认后：按顺序每批 `git add <文件>` + `git commit -m "<信息>"`。不 amend。不 push。
7. 被拒绝（用户回「不行」「我自己来」「manual」或对计划有任何异议）：停下。不要再出第二份计划。用户会手动提交，等他们确认后你直接跳到 3.5。

规则：
- 任何地方都不 `git commit --amend` —— 三段三类提交（工作提交 → 归档提交 → 日志提交）。
- 这一步绝不推到远端。
- 用户只想改提交信息措辞、接受文件分组的，改好信息再确认一次；但他们要是否定了分组，就转手动。
- 整份计划是一次提问，不要每个提交问一次。
```

分组靠的是模型记得自己这个会话改过哪些文件，程序不记录。

## 归档、写日志，下一次会话从文件里接 { #finish-work }

**问题**：明天新开一个会话，模型不知道今天做完了什么、提交了哪几个 commit、还剩什么。

**功能**：用户输入 `/trellis:finish-work`。命令不提交代码——那是 3.4 的事——只做三件：看状态、归档任务、写一条日志：

```text title="译文 · /trellis:finish-work"
# 收尾

收尾这个会话：归档活动任务（以及用户想一并清理的其他已完成未归档的任务），记录会话日志。代码提交不在这里做 —— 那在调用本命令之前的阶段 3.4。

## 第 1 步：看当前状态
运行 `get_context.py --mode record`，它打印：
- 我的活动任务 —— 看除了当前任务，还有没有别的其实已经做完（代码已合并、验收标准已满足），这一轮该一起归档。
- Git 状态 —— 快速看一眼哪些是脏的。
- 最近的提交 —— 第 4 步的 `--commit` 要用它们的哈希。
如果列出了与当前会话无关的其他已完成任务，向用户一次性确认：「这 N 个任务看起来已完成 —— 这一轮一起归档吗？[y/N]」。默认不。当前活动任务在第 3 步无论如何都会归档。

## 第 2 步：核查 —— 给脏路径分类
运行 `git status --porcelain`。滤掉 `.trellis/workspace/` 和 `.trellis/tasks/` 下的路径 —— 它们由 `add_session.py` 和 `task.py archive` 的自动提交管，作为本命令自己的工作会显示为脏。
剩下的每个脏路径，判断它属于当前任务，还是别的并行工作（比如另一个终端窗口在改同一个仓库）。判断依据：
- 当前任务的 `prd.md` / `implement.jsonl` / `check.jsonl` 里提到的路径 → 当前任务
- 落在任务声明范围的代码区域里，或者你记得这个会话改过的 → 当前任务
- 在你不记得碰过的无关区域 → 别的并行工作
然后分流：
- 剩下的路径里有像当前任务的改动 —— 中止并说：「工作区里有这个任务未提交的代码改动：<清单>。先回到阶段 3.4 提交，再运行 /trellis:finish-work。」这里不要运行 git commit，也不要催用户提交。用户回到 3.4，由 AI 在那里主导分批提交。
- 剩下的路径看起来都无关（别的窗口的工作）—— 报告一次然后继续第 3 步：「提醒一下，任务范围外有脏文件 —— 留给另一个窗口：<清单>。」
- 真拿不准 —— 问用户一次：「<清单> 是这个任务我忘了提交的，还是另一个窗口的？（提交 / 忽略）」—— 按回答分流。

## 第 3 步：归档任务
运行 `task.py archive <任务名>`。至少归档当前活动任务（如果有），加上用户在第 1 步确认的其他任务。每次归档由脚本自动提交一个 `chore(task): archive ...`。
没有活动任务、用户也没确认要清理，就跳过这一步。

## 第 4 步：记会话日志
运行 `add_session.py --title "会话标题" --commit "hash1,hash2" --summary "简短总结"`。
`--commit` 用阶段 3.4 产生的工作提交的哈希（第 1 步的「最近的提交」里有，或者 `git log --oneline`）。不要带第 3 步归档提交的哈希。这一步产生一个 `chore: record journal` 提交。

最终的 git log 顺序：<3.4 的工作提交> → `chore(task): archive ...`（一个或多个）→ `chore: record journal`。
```

## 上次怎么解的：翻宿主自己的会话记录 { #mem }

**问题**：用户说「上次那个 CSV 乱码是怎么解决的？」，答案不在任何 `prd.md` 或 spec 里，只在三周前的一次对话里。

**功能**：`trellis mem` 是一个本地命令行，直接读各家宿主存在本机的会话记录（Claude Code 的 `~/.claude/projects/`、Codex 的 `~/.codex/sessions/` 等七家），能列出、搜索、按 Trellis 任务的边界切片、导出清洗过的对话。切片的边界就是 `task.py create` 和 `task.py start` 两条命令：`--phase brainstorm` 取规划那段对话，`--phase implement` 取执行那段。

描述：通过 `trellis mem` 命令行回到过去的 AI 对话历史。只要用户问「上次 X 是怎么解决的」「这个我们讨论过吗」「X 当时怎么定的」「提醒我这个任务里我们做了什么」「上次怎么解的」「之前讨论过吗」「想起一段对话」，或者开始一次和以前的工作有重叠的头脑风暴、调一个似曾相识的 bug、跨会话继续一个任务、做收尾复盘时，就用它。返回原始的历史对话；当场决定是更新 spec、追加到任务笔记、在回答里引用，还是只是记在心里。

这个 skill 教 AI 怎么调用 `trellis mem` —— 项目的跨会话记忆原料 —— 以及什么时候伸手去拿它是对的。

它有意是一个能力 skill，不是一道流程。没有固定的输出文件，没有必须写回的步骤，没有「每次 finish-work 之后都要跑」的规则。拿到 `mem` 的结果之后怎么处理，是对话当下的判断。这个 skill 存在，是为了让 AI 知道有这个能力、能自己决定。

……`mem` 里的东西一样都不上传。全部在本地读。

## 什么时候用

标准是「一个资深队友会不会问『这个我们不是讨论过吗？』」—— 那就是时候。一些具体模式：
- 头脑风暴重来的风险。开始一个新任务，碰到用户以前做过的区域，想先查有没有已经定下的决定 —— 在重新问用户之前。
- 似曾相识的 bug。当前 bug 的样子像用户以前报过、修过的。翻出那次会话能省一整轮调试。
- 跨会话继续。用户隔了一阵回来，说「我们做到哪了」「继续上次的」，又没说具体。
- 找决定。用户提到「我们关于 X 定的那个」，但决定只在一次旧的头脑风暴里，不在任何 prd.md / spec/ 里。
- 收尾复盘。用户明确要求总结这个任务定了什么、哪里痛、哪里意外时 —— 不是每次 finish-work 都强制跑。
- 跨工作找规律。用户问「我是不是老在 X 上犯同一个错」「我每次都踩这个坑吗」—— 跨会话搜索能回答。

这些都不沾边，就别调 `mem`。它是工具，不是仪式。
