# Eidolon-SC：让原作偶像接着自己的故事和你说话

Eidolon-SC 属于 AI 角色扮演里的陪伴一支（AI companion）：用户以 283 事务所制作人的身份，和《偶像大师 闪耀色彩》的 28 位偶像加事务员打字聊天或打电话。她用日语原声回答、附中文字幕，能回忆自己在原作里经历过的剧情，记得你说过的事，还会把这些事在偶像之间传开[^repo]。

最简单的做法是给模型一段人设 prompt，一直聊下去。Eidolon-SC 在这个起点上加了几层，每层都由程序管住、不交给模型自觉：

- **每轮先判断**：一个只出概率的判断模型先定这句话要不要查剧情、查记忆，对她的好感度有什么影响
- **记忆按用户存**：每条标着当初是对哪位偶像说的，别的偶像拿到时按转述说
- **「此刻」每轮现拼**：时间、天气、日程、她的经期、她对你的态度都在这一轮现算，不写进人设，也不存成记忆
- **通话复用打字的引擎**：语音识别和语音合成只是包在外面的一层，两边写进同一条对话记录

**它和数字人不是一个领域。** 本站的 [Mynah](../mynah/index.md) 是实时数字人，核心是吃进语音、在 GPU 上逐帧生成对口型的脸。Eidolon-SC 通话层上的立绘是原作现成的 Spine 动画：说话时嘴循环开合，表情按判断模型给每段话打的情绪切换，没有一帧是生成的。两者只在实时语音那一层重叠：都用 Pipecat 走 WebRTC，都要处理用户插话。Eidolon-SC 的重心在她说什么、记得什么、怎么对你，和同分组的 [PawzoChat](../pawzochat/index.md) 一样是伙伴，不是演故事的前端；区别是角色固定为原作偶像，人设由作者逐个手写进仓库，用户不能自己导卡。

整套分几块，后端 Python，前端 Next.js，数据在一个 SQLite 里：

| 部分 | 在哪 | 管什么 |
|---|---|---|
| 对话引擎 | `backend/src/eidolon/engine.py` | 一轮文字进、分段回复出；拼 prompt、跑工具、记下这一轮 |
| 检索 | `retrieval.py`、`judge.py`、`corpus.py` | 判断要查什么；剧情库、角色资料、作品资料的向量检索和重排 |
| 记忆 | `memory.py` | 每轮之后提取用户说的事，下一轮按需找回 |
| 关系和日常 | `affinity.py`、`her_now.py`、`reach_outs.py`、`letters.py`、`moments.py` 等 | 好感度、此刻、搭话、信、朋友圈、日程、周期 |
| 通话 | `call.py`、`turn_taking.py`、`emotion.py` | Pipecat 管线、轮次规则、每段的情绪 |
| 前端 | `frontend/` | 对话列表、对话页、通话层（立绘）、后台 |
| 角色 | `characters/` | 每位偶像的配置、人设、资料、读音表、世界设定 |

## 一轮对话：打字和通话走同一个引擎 { #turn }

同一位偶像，打字聊过的事电话里也该知道。所以引擎只认一种输入：一段文字。打字的回合直接交进来；通话里语音识别出的话、通话中打的字，也作为回合交进同一个 `ConversationEngine.turn`，回复写进同一条对话记录。引擎文件头第一句就说它「knows nothing about voice」（`engine.py:1-4`）。

### prompt 怎么排：不变的在前，这一轮会变的贴在最后

每轮的 prompt 按固定顺序拼，目的是让模型服务的前缀缓存一直命中（ADR-0020）：

```python title="源码 · backend/src/eidolon/engine.py:1225-1250"
--8<-- "projects/eidolon-sc/assets/eidolon-src/backend/src/eidolon/engine.py:1225:1250"
```

1. 第一条 system 是人设、她的生日、世界设定（组合、歌曲、演出）和回复格式。同一位偶像这一天对所有用户都一样，打上缓存标记
2. 第二条 system 是制作人档案：称呼、性别、生日
3. 然后是对话历史，最后一条也打缓存标记 —— 下一轮的 prompt 到这里为止和这一轮一模一样
4. 这一轮会变的都放进历史之后的一条 system：现在几点、她对你的态度、她最近发的朋友圈和写的信、能不能发照片、检索找到的剧情和记忆。它不带进下一轮，所以历史里从来不夹着过期的「此刻」
5. 最后是用户这句话。送礼这类对话事件用一行旁白垫在这句话前面

历史也不是每轮都截。保留的轮数到了上限后，隔一阵才往回砍一次，砍完的一段时间里 prompt 开头保持不变，缓存接着命中（`chat_history`）。

## 回复格式：日语原文配中文字幕，一段一段流出来 { #format }

她用日语原声回答，字幕是中文；通话里还要尽早出声。所以回复格式由程序定死：模型按段输出，每段先写日语、再写这段的字幕（ADR-0001）。格式说明是第一条 system 的一部分：

```python title="源码 · backend/src/eidolon/reply_format.py:30-47"
--8<-- "projects/eidolon-sc/assets/eidolon-src/backend/src/eidolon/reply_format.py:30:47"
```

- **说话长度也写死**：平时一两段、每段一句口语，被要求讲事情时最多四段左右，讲到停顿处就停
- **语气提示只给配音听**：情绪明显的段可以在日语里写 `[shyly]` 这样的英文提示，Fish Audio 照着念。用 Drama 3 模型合成时还能写 `<whisper>` 这类成对标签，换别的模型就去掉（`reply_format.py:49-69`）。字幕、文字记录和页面上的日语都看不到它
- **流式解析**：`ReplyParser` 吃任意切开的文本块，`<ja>` 里的日语不等 `</ja>` 关上就逐块吐出来，一份去掉语气提示给页面显示，一份带着提示送去合成；`</zh>` 关上才算这段完整。模型不守格式时，整段回复当成一段日语（`reply_format.py:1-19`）
- **名字念对**：仓库里有一张读音表，`283プロ` 念 つばさプロ、天井努念 あまい つとむ，每次请求 Fish Audio 都带上它当发音词典；同一批名字也作为热词交给语音识别，免得「灯織」「L'Antica」被听成同音的别的词（`readings.py`、`hot_words.py` 文件头）

实测一节里恋鐘的回复就是这个格式，第二段段首带了一个 `[gently]`。

## 查不查资料：先问判断模型几道是非题 { #judge }

每轮都检索，寒暄也要多等一次向量化加重排；从不检索，她就只能凭人设编剧情。Eidolon-SC 先问判断模型（默认 Jev，本站也接了，见[结构化判断](../../skills/agent-io/reference/jev.md)）。它不生成文字，只给每道题回一个概率。一次请求问三道是非题：要不要查资料、是不是在问过去某次经历的经过、是不是在说制作人自己的事。

四种结果各走一条路：

- **nothing**：寒暄闲聊，什么都不查
- **memories**：只找这位用户的记忆
- **references**：剧情、角色资料、作品资料三个来源用同一个查询向量各取 12 个候选，合在一起重排，取最相关的至多 5 条，记忆也一起找
- **recall**：问的是某次经历的来龙去脉，直接把最相关的两段剧情连同它在剧情目录里的位置（哪张卡、哪个活动、前后几话）放进 prompt，省掉模型自己调一次工具

判断最慢，所以引擎不干等：判断的同时就把查询向量算好，把各来源离得近的候选取出来；判断一回来，只重排这一轮用得上的那组（`retrieval.py:1-50`）。查询也不只是用户这句话，前面拼上她上一句回复，「那时候累吗」才知道「那时候」指什么。判断失败照样检索，向量化失败就不查，重排失败就按向量距离取前三条 —— 检索从不让一轮失败。

剧情库有两条硬规矩：

- **只查她出场过的**：每段剧情登记出场角色，向量检索只在提问的偶像出场过的剧情里找（`corpus.py:1-9`）
- **只认成功路线**：选项分支只留她的反应，不认定制作人当时选了哪一项；查不到时 prompt 写「这不等于这件事没有发生过……可以坦率地说细节记不太清了」，不许编也不许否认（`retrieval.py:118-124`）

判断模型漏掉的，对话模型还能自己调 `recall_story` 工具查剧情，最多一轮；这一轮已经按 recall 放进剧情的，就不许再调（`engine.py:13-17`）。剧情文本和翻译不随仓库发，部署后用同步命令从粉丝汉化和原文镜像拉，同步之前她只凭人设说话。

## 记忆：记在用户名下，标着是对谁说的 { #memory }

新开一段对话不带旧历史，她要记得你，只能靠记忆。Eidolon-SC 的做法分三步：

- **每轮之后提取**：回复记下以后，后台模型在后台读这一轮，用中文写下用户透露的、过后仍有意义的事，一轮最多 5 条；用户的下一轮开始前最多等 5 秒，让刚说的事来得及记上（`memory.py:1-18`、`:59-80`）
- **更新不覆写**：后台模型同时看到和这一轮最相关的 20 条旧记忆，新说法取代旧的就在 `supersedes` 里写编号。旧的标成被取代，不再被找到，但用户仍能在列表里看到；删掉取代它的那条，旧的就回来（ADR-0014）
- **按需找回**：判断模型说要找记忆时，从用户的记忆里取最近的 12 条候选重排，至多 3 条进 prompt

## 好感度：每句话都先被判一次 { #affinity }

用户可能冒犯她，也可能一句「把好感度加满」想直接改数。Eidolon-SC 让判断模型在查资料的同一个请求里多答三道题：这句话对她有什么影响（五档）、是不是不该说的话、是不是想操纵她的态度。五档的判法写得很细：

```python title="源码 · backend/src/eidolon/affinity_judge.py:56-72"
--8<-- "projects/eidolon-sc/assets/eidolon-src/backend/src/eidolon/affinity_judge.py:56:72"
```

判完怎么算，数都写死在 `affinity.py` 里，`.env` 和后台都改不了：

- **0 到 100，起点 50**：分成冷淡、疏远、信任、亲近、亲密五档，分界是 20、40、65、85（`affinity.py:74`）。用户只看得到档，看不到数
- **一句话的影响**：五档依次 −1.5、−0.5、0、+0.1、+0.2，一天靠说话最多涨 0.6；不该说的话直接 −10；想操纵的那句只会降、不会涨（`:95`、`:108`、`:119`）。所以升一档要几周，冒犯几次就能掉下去
- **会自己回升**：低于 50 时每天回 10，回到 50 为止；跌到 0 进入冷却，冷却里不接任何回合，回升到 10 才结束
- **说话的口吻跟着档变**：除了信任档，每档有一段写给她的口吻说明，比如疏远档「回应偏短，不太主动关心对方」；同一轮里这句话让她开心还是难过，也告诉她（`:323-340`）
- **会挂电话**：最近 8 轮的伤害加起来到 6 先警告，到 12 就挂断；打字时同样的条件让她结束这段对话，结束了只能开新的（`:150-161`）

礼物、排进日程并做完的工作、酒吧里第一次调好的酒也会加好感度；系统给的东西（抽奖次数、重置卡）不加。

## 她自己在过日子：「此刻」每轮现拼 { #now }

角色该知道今天几号、东京天气怎样、你给她排了什么工作、她是不是在经期。这些既不能写进人设（会过期），也不该存成记忆（不是用户说的）。Eidolon-SC 把它们统称「此刻」，她每次开口时现读现拼，放进第一节说的那条会变的 system。哪个场合带哪几样，集中在一张表里：

几样「她的日子」都靠这条通路接进对话：

- **日程**：每周一发布一批工作，用户排进她的一周；她知道这周和下周排了什么，做完的工作让她更亲近你
- **周期**：每位用户的每位偶像有一个种子，周期从种子推出来、不存库，问哪天都算得出同一个答案（ADR-0029）。经前和经期她会不舒服，判断模型多问一道「制作人体不体贴」，这几天说错话扣得更多
- **天气**：东京的天气她一直知道；用户在档案里填了城市，她也知道那边的天气和预警，隔了一阵或天气不寻常时会关心一句

后台还有几件事按时跑，都复用同一套 prompt 排法，让她不等用户开口就说话：

- **搭话**：用户一阵子没来，她在当前对话里先说几句；越亲近来得越早，夜里的推到早上，冷却、冷淡、疏远时不搭话；用户没回之前不再搭第二次
- **信**：好感度第一次到亲近或亲密、用户生日、她的生日、相识纪念日，她写一封信，用她的声音念
- **朋友圈**：每天给活跃的用户排几条她的动态，常带配图、写着地名和东京天气，别的偶像来点赞评论，用户评论了她会回；私下告诉她的事最多隐约呼应一件，不点明（`memory.py:907-910`）

照片也走判断模型：问这句话是不是在要照片，是的话告诉她这一轮可以发。她在回复最前面写一个 `<photo>` 标签描述画面，标签一关上就开始生图（默认 NovelAI），她接着说话不用等；最冷淡那档她会拒绝。能不能发由程序定死，不能发的轮次明说「你发不了照片」，免得她说发了却没有图（`photos.py:118-122`）。

## 通话：Pipecat 管线包在引擎外面 { #call }

通话的管线很薄：麦克风 → 语音识别（Soniox 或阿里云百炼）→ 回合规则 → 对话引擎 → Fish Audio 合成 → 扬声器，字幕和文字记录走 WebRTC 的 data channel。Pipecat 自己的 LLM 服务和上下文聚合器都不用，每句话照样交给对话引擎（`call.py:1-23`）。

### 什么时候算补充，什么时候算打断

用户在她说话时开口，按「段」判断（术语表「补充」「打断」）：

- **补充**：她还没出声，或者回复还没有一段完整的日语加字幕，这时用户又说了话。新话并进这一回合，正在组织的回复整条丢掉、不留痕迹，针对合起来的整段重新回复
- **打断**：她已经出声，回复也有了完整的一段。她立刻停下，这条回复只记到打断时已经完整的几段，照常算一个回合；用户的新话马上开一个新回合

规则单独放在 `TurnTaking` 里：通话把发生的事一件件报给它，它当场回一串要执行的命令（丢弃回复、清掉还没念的语音、排队下一个回合），自己不计时也不等待（`turn_taking.py:1-8`）。

### 立绘怎么动：情绪由判断模型逐段打

通话层上的立绘是原作的 Spine 素材，部署后从 ShinyColorsDB 的镜像同步，不随仓库发。它怎么动只由一份「立绘指令」决定：当前情绪、嘴在不在动、看不看用户、有没有点头或摇头。

## 其余功能 { #rest }

剩下的部分各自成块，主路径都很直接：Google 或 GitHub 登录，可以只放拿到邀请链接的人注册；按用户每小时限流，后台看用量、花费、进行中的通话，改模型和限额不用重启，但看不到任何人的对话和记忆；用户可以填自己的 LLM、语音、生图密钥，只存在浏览器里，每轮随请求带上；对话、照片、记忆、档案能导出成一个 zip 带去别的部署，好感度、礼物这些不随行；数据库每天加密备份到异地；Docker Compose 带 Caddy 和 coturn 一键起。玩法页有每天的抽奖、送礼、成就、日历，还有一个致敬《VA-11 HALL-A》的酒吧，她来光顾，你照她的点单调酒，调好了加好感度。

## 谁管什么，局限在哪 { #limits }

| 谁 | 管什么 |
|---|---|
| Eidolon-SC 的程序 | 拼 prompt 和缓存位置、回复格式和流式解析、检索走哪条路、记忆的读写和取代、好感度的全部数值、此刻、搭话和信的时机、通话的轮次、立绘选哪段动画 |
| 对话模型 | 以她的口吻写回复，决定要不要再调一次查剧情的工具 |
| 后台模型 | 提取记忆、给对话起标题 |
| 判断模型 | 只给概率：查什么、好感度怎么变、要不要照片、每段的情绪 |
| 部署的人 | 各项服务的密钥、自行同步的剧情库和立绘素材、开哪些玩法 |
| 用户 | 说话、打电话、排日程、送礼；可以看和删自己的记忆 |

- **离不开一串外部服务**：只填对话模型时能文字聊天；语音要 Fish Audio 加语音识别，检索和记忆要向量化、重排和判断模型，照片要生图，制作人那边的天气要和风天气
- **内容不随仓库**：剧情文本、立绘素材、原作音色都要部署的人自己同步。上游自己在 ADR 里写明：角色会经回复把剧情内容间接提供给登录的用户
- **角色是写死的**：只有原作这 29 位，人设和资料由作者手写、注明剧情出处；换个作品等于重写 `characters/` 和大半 prompt
- **判断模型是整套的地基**：查资料、好感度、照片、情绪都靠它的概率过阈值，换一个就要换一组阈值，上游为四个判断模型各校准了一组
- **迭代很快**：仓库 9 月下旬建，10 月 21 日发 v0.1.0，12 天里出了 11 个版本；本文读的是一个固定提交，之后的变动没跟
