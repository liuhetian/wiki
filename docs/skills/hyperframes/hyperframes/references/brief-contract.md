# Brief 契约

意图层（`/hyperframes` → `references/intent-interview.md`）只问一次创作问题。执行的工作流把确认后的结果写进 `BRIEF.md`，不再重问这些问题。本契约定义规范的运行形态字段、共享的 brief 字段和提问规则。各路由专属的选项在 `/hyperframes` → `references/routes/<workflow>.md` 里。

## 目录

- [运行形态](#1-run-shape)
- [共享字段](#2-shared-fields)
- [提问协议](#3-question-protocol)

## 1. 运行形态 { #1-run-shape }

三个术语描述的是不同的关注点。不要拿一个替代另一个。

| 术语 | 取值 | 负责 |
| --- | --- | --- |
| `flow` | `automation` 或 `companion` | 由谁驱动执行。`companion` 一律在 `/general-video` 里执行。 |
| `storyboard` | `yes` 或 `no` | 构建之前是否评审计划和布局（`review-loop.md`）。 |
| `mode` | `collaborative` 或 `autonomous` | 后续的偏好闸门和检查点闸门如何表现。用户从不直接选择这个标签。 |

根据确认后的运行形态推导一次 `mode`：

| `flow` | `storyboard` | 推导出的 `mode` |
| --- | --- | --- |
| `companion` | 任一取值 | `collaborative` |
| `automation` | `yes` | `collaborative` |
| `automation` | `no` | `autonomous` |

只有当旧项目缺少足够的状态来推导模式时，才默认用 `collaborative`。`/motion-graphics` 按设计就是自主的，不需要那两个运行形态问题。

### 信号与持久化

- 在意图捕捉期间出现的持续性信号，比如"给我个惊喜"、"你替我决定"、"直接做吧"或"别再问了"，会设置 `flow: automation`、`storyboard: no`，从而得到 `mode: autonomous`。
- 在检查点上一句单纯的"go"（开始）或"看起来不错"只接受那个检查点。它不改变模式。
- `STORYBOARD.md` 存在之后，把推导出的模式持久化到它的 frontmatter 里。恢复运行时，`STORYBOARD.md` 里显式写的 `mode` 优先于推导结果，因为它可能代表用户后来的改动。
- 运行中途的"别问了，做完它"只改变检查点的行为。文件存在时，把 `STORYBOARD.md` 的 `mode` 设为 `autonomous`。不要改写已经确认的 `flow` 或 `storyboard` 字段。
- 只有在出现"我们一起评审吧"这类明确信号之后，才恢复协作式检查点；普通的反馈不改变模式。

### 闸门行为

| 闸门 | 协作 | 自主 |
| --- | --- | --- |
| 偏好：preset、声音、字幕风格（caption identity） | 工作流标为必需时就问。 | 自行决定，并用一行理由说明所做的选择。 |
| 检查点：计划、草图、渲染前评审 | 问，并等待。 | 发出同样的总结，然后继续。 |
| 质量：抓取完整性、`lint`、`hyperframes check`、工作流自身的验证 | 运行，出错就停。 | 运行，出错就停。 |
| 路由歧义 | 明确化解；路由错了会改变交付物。 | 要求相同。 |
| 未登录或凭据不可用 | 显示状态，等待用户登录或明确选择离线方式。 | 显示状态，并通过一个可用的离线提供方继续。 |

自主模式绝不悄悄丢掉一项必需能力。如果选定的工作流对它没有本地、缓存或离线的提供方，就把阻塞点报出来，而不是省略这项能力。凭据问题不会放宽质量闸门。

两种模式下，渲染都仍要由用户放行。检查通过后，两者都打开最终的 Studio 预览并问"现在渲染，还是要改什么？"；在自主运行中，这是唯一保留的问题。拿到回答之后才渲染。

### 检查点反馈

检查点反馈以聊天回复的形式到来。只修改它点名的帧，然后重新呈现这些帧。

自主不等于沉默：用可见的决定和简短的理由替代被吸收掉的问题。每一次自主的画面或视频交付，都要按情况写明最终的预览或渲染产物，对有时长的交付物报告实际时长，并在可用时附上一张联系表（contact sheet）或快照表（snapshot sheet）以及相关的帧标识。多场景的作品取各场景的中点；单场景的作品取一个或多个证明时间点。这样即使中间的检查点没有暂停，用户也有一个可供评审的界面。

## 2. 共享字段 { #2-shared-fields }

只问选定路由会用到的字段。路由条目会标明它的必答问题和延后问题。按策略推断或推导出的值写进 brief 里说明，而不是去问。

| 字段 | 含义 | 策略 |
| --- | --- | --- |
| `flow` | 由谁驱动执行 | 当路由同时支持两种 flow 时，在意图捕捉的最后问。自主信号即是它的回答。 |
| `storyboard` | 构建之前是否评审计划和布局草图 | 当路由支持分镜时，在 `flow` 之前问。分镜请求即是它的回答。 |
| `destination` | 视频将在哪里播放 | 从请求中推断。只有在未知且答案会改变画幅、字号层级或构图时才问。 |
| `aspect` | 画布尺寸 | 从投放渠道推导：社交信息流 → `1080x1080`；TikTok/Reels/Shorts → `1080x1920`；YouTube/网站/桌面 → `1920x1080`。说明推导过程。 |
| `length` | 目标时长 | 让工作流推荐一个素材撑得起的范围；附上理由。 |
| `language` | 旁白和字幕的语言 | 使用用户的语言，并说明这一点。 |
| `audience` | 谁会看 | 明确时就推断。只有不同的答案会改变故事或用语时才问。 |
| `message` | 视频必须传达的那一件事 | 推导出来，并用一句话复述确认。在它明确之前不要做分镜。 |
| `angle` | 路由专属的故事形状 | 推荐一个路由定义好的选项，并附上理由。 |
| `narration` | `yes`、`minimal` 或 `no`，外加路由专属的模式 | 遵循选定的路由。 |

### 记住的默认值

令 `<MEDIA_DIR>` 为已安装的 `/media-use` skill 目录。令 `<MEMORY_ROOT>` 为已有项目的根目录。在搭建脚手架之前，使用一个故意不存在、且没有任何 `.media` 祖先目录的探测路径，比如 `/tmp/hyperframes-intent-memory-<run-id>`；绝不用当前工作区作探测路径。用下面的命令读取合并后的偏好：

```bash
node <MEDIA_DIR>/scripts/prefs.mjs get --hyperframes <MEMORY_ROOT> --json
```

对于项目创建前的探测，`<MEMORY_ROOT>` 就是那个不存在的探测路径，所以只有个人层级能提供值。如果那个路径已经存在或含有 `.media`，就换一个。真正的项目存在之前，不要声称值来自项目。

记住的值会成为推荐答案，并写明它的来源。它绝不推翻当前请求，也绝不跳过必需的问题。确认过的配方则不同：采用这套组合可以填好它包含的字段，因为采用本身就是确认。

只记录用户确认过的值，绝不记录仅仅是推断出来或默认的值。记录发生在工作流写出 `BRIEF.md` 之后；支持的键列在 `brief-format.md` 里。用户看到推荐并接受了它，就算确认了。个人默认值只按 `/media-use` 的记忆规则晋升。

项目第一次记录偏好时，用简短的一句话说明它会在以后的运行中被记住。不要仅仅因为某次自主构建复用了一个记住的值就重新记录它；只有当前运行里的确认才会产生新的记忆事件。

## 3. 提问协议 { #3-question-protocol }

遵守以下不变量：

1. 只问会实质影响输出、且尚未回答的字段。
2. 每条消息只问一个字段，等到回答后再问下一个字段。
3. 把推荐选项放在第一位，并附上简短理由。可以用编号选项列表，但列表里的每个选项都必须回答同一个字段。选项列表适合事实类字段（投放渠道、时长、语言），在那里它能帮助回忆；请求尚未定型的创意类字段（message、angle、语气）要用有锚点的开放式问题 —— 在那里给列表会引导答案，而不是收集答案。
4. 当前请求已经回答了的问题就跳过。光靠推断不算回答。
5. 最后先问 `storyboard` 再问 `flow`，而且只对支持它们的路由问。
6. 在交接之前预告延后的问题；不要事后让用户措手不及。
7. 出现自主信号时，不再问剩下的任何偏好或检查点问题。说明补全后的 brief 和各项决定的理由，然后开始构建。
8. 有原生提问 UI 时就用它。否则发一条纯文字问题，附一个编号选项列表；绝不把几个字段放在同一个列表里。
9. 在交接总结之前，做一次整合检查：找出所有答案组合起来才产生、而单个答案看不出来的后果，并带着调整建议把它提出来。
10. 交接总结把用户明说的字段和推断或默认的字段分开，两组都附上依据。
11. 修改不等于确认：总结被修正之后，呈现更新后的总结，确认后再执行。

在检查点上，"go"（开始）接受的是那个检查点上显示的推荐。如果某条消息明确呈现了一份完整的 brief，并说明"go"会接受所有显示出来的默认值，那么"go"可以确认那整份显示出来的 brief；没有那句话，就不要假定用户接受了更大的范围。
