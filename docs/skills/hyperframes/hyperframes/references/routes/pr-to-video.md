# 路由：pr-to-video

- **输入：** 一个 GitHub PR URL、`owner/repo#N` 或"this PR"（这个 PR），通过 `gh` 读取；它不是网站抓取请求。
- **输出：** 一支更新日志、功能揭晓、修复讲解或重构导览视频，包含 diff、前后对比、文件树和影响等场景。硬上限约 3 分钟；时长随改动规模而定。
- **触发：** "给这个 PR 做个视频"、"把 PR #1187 做成更新日志视频"、"根据这个 pull request 做个发布说明视频"。

## 访谈

- **必答项：** **PR 引用**（URL、`owner/repo#N` 或"this PR"）· **角度（angle）** —— 更新日志 / 功能揭晓 / 修复讲解 / 重构导览，推荐 PR 本身所提示的那一种 · **受众（audience）** —— 开发者（默认）· 技术背景混合 · 非技术的相关方 · **时长** —— 依据下面的规模表 · **投放渠道** —— 代码讲解默认 16:9。
- **时长取决于 PR 的改动规模**，而不是一个固定的猜测 —— 只读地看一眼（工作流的 Step 1 仍会做完整的确定性抓取）：

  ```bash
  gh pr view <PR_REF> --json title,additions,deletions,changedFiles
  ```

  根据 `additions + deletions` 选档位（`changedFiles` 多时往上调），并以它作为首选推荐（硬上限约 3 分钟）：

  | PR 改动规模 | 推荐时长 |
  | --- | --- |
  | 微小（≲ 50 行改动） | 约 20–40 秒 |
  | 聚焦（约 50–200 行） | 约 40–70 秒 |
  | 较大（约 200–600 行） | 约 70–110 秒 |
  | 大型（≳ 600 行，或 25 个以上文件） | 约 110–180 秒 |

  用一句话说明依据（"约 40 秒 —— 小改动，12 个文件 +44/−13"）。档位是 diff 能撑起多少故事的**上限**，绝不是必须填满的下限：只有一个主线标题的故事，无论档位如何都推荐 30–90 秒之内（档位的范围仍可作为一个非推荐的、更完整的导览选项出现）。

- **提案轮：** `angle` 和开场钩子 —— diff 定下的是事实，不是讲法。
- **运行形态：** 两个问题都问。
