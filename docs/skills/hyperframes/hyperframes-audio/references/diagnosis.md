# 诊断你听不到的音频

`SKILL.md` 里的症状表是从"听起来发轰"开始的。这预设了已经有人听过并且这么说了。如果别人只丢给你一个文件和一句"修一下"，你手里没有这样一句描述——而且你听不到。本文讲的就是如何得到这样一句描述。

首先值得直白地说明这件事有多难，因为它的失败模式不是"没有答案"，而是**一个自信的错误答案**：

> **单个未知人声的绝对频谱是无法诊断的。**

每一条人声都有起伏，其幅度恰好和一个人为加上的滤波器差不多大。共振峰有 ±10 dB 的起伏。一个说话人的基频可能落在 85 到 255 Hz 之间的任何位置。按照普通的韵律，句子从开头到结尾会下降 5–6 dB。单独看一张频谱，你会在每个地方都发现"缺陷"，而你发现的那些其实都是说话人本身。

所以诊断永远是**比较**。整个方法就在于选对用来比较的东西。

---

## 和同一个文件内部的东西比较

按能告诉你多少信息排序。优先用排在最前面的那个可用的参照。

### 1. 干净的原始版本（如果有的话）

如果磁盘上有未受损的那条录音，那这就是全部工作——两个都测，相减，差值*就是*缺陷。下面没有任何一种方法比它更好。在做别的之前先找找它。

### 2. 停顿

存在于单个文件内部的最强参照。语音停下来了；间隙里仍然存在的东西就不是人声。

**它能回答的问题："是不是加了什么东西？"**

停顿里任何能听到的东西都是叠加上去的——嗡嗡声、低频隆隆声、嘶嘶声、房间底噪。它是叠在上面的，所以可以减掉，而且这是一个可靠的阳性发现。

**它不能回答的问题："是不是被滤波了？"**——把这一点搞反，正是这个方法产出自信错误答案的途径。

滤波器做的是乘法。把它应用到一个间隙本来就处在量化底噪的文件上，间隙仍然停留在量化底噪：近乎静音乘以任何东西仍然是近乎静音。所以停顿里不会留下它的任何痕迹。在一条录音上测量，对整个文件施加一个 2.5 kHz 以上 −9 dB 的搁架：

|                   | 1 kHz | 5 kHz | 倾斜      |
| ----------------- | ----- | ----- | --------- |
| 停顿，未受损  | −91.0 | −91.0 | +0.0      |
| 停顿，施加搁架    | −91.0 | −91.0 | **+0.0**  |
| 语音，未受损 | −34.7 | −42.8 | −8.1      |
| 语音，施加搁架   | −35.4 | −48.5 | **−13.1** |

缺陷在语音里是清清楚楚的 5 dB，在停顿里则**恰好为零**。

所以：**绝不要用停顿频谱上的阴性结果来排除 EQ。** 有一次运行恰恰这样做了——测了停顿，发现它很平滑，于是得出结论"任何类型或 Q 值的静态 EQ 都被排除了"——接着就把一个听不见的 −72 dBFS 低频隆隆声当成了缺陷，给一个真正问题是缺少高频的文件交付了一个 high-pass。

只有当间隙里带有真实录制的、经过同一个滤波器的底噪时，停顿频谱*才*是一个传递函数。一段房间底噪垫底是这样的；一条数字上干净的录音则不是。在信任它之前，先确认你手上的是哪一种：如果间隙离量化底噪只有几 dB，这个参照只能找到叠加的内容，别的什么都找不到。

### 3. 语音自身的倾斜，用于怀疑存在滤波器的情况

当停顿看不到滤波器时（见上文），唯一还带着它的只有语音。读取跨越几个 1/3 倍频程频段的倾斜，而不是只看某一个——`1k / 3.2k / 5k / 7k` 就足以看出一个搁架：

```bash
for f in 1000 3200 5000 7000; do third voice.wav $f; done
```

语音在大约 1 kHz 以上会稳定地衰减，所以向下的斜率是预期之中的；你要找的是一个不断变陡的斜率，或者一个台阶。在上面的表里，从 1 k 到 5 k 下降 −8.1 dB 是一条普通的人声，而 −13.1 dB 是同一条人声被削掉了 9 dB 高频。

**这是一个候选，不是结论。** 普通的斜率在哪里结束、缺陷从哪里开始，取决于说话人，而你没有这个说话人的基线。说清楚你测到了什么、它意味着什么，然后让能听的人去听。

### 4. 文件随时间与自身比较

对于任何与电平相关的问题，把每一段和这条 track 自己的中位数比较，而不是和一个目标值比较。`levellingResult` 做的就是这件事，这也是为什么一条本来就均匀的 track 处理完回来时原封不动。

## 不要拿另一条人声来比较

产生本页内容的那次评估中，两个错误答案都来自外部参照，而且两者都是在错误的基础上严谨论证出来的：

- **公开的平均频谱**（LTASS 之类）。有一次运行得出结论"7 kHz 以上 +10 dB，对半拆分稳定，与门限无关"，而那个文件真正的缺陷是 200 Hz 处 +6.6 dB。它的支撑论据——10 kHz 比 6.3 kHz 高 6.2 dB——复核时测出来只有 0.6 dB，而且在干净的原始版本里测出来也一样。公开的曲线混合了不同性别、不同语料库和不同麦克风；它们和任何一个说话人之间的差距都比大多数缺陷更大。
- **合成的对照人声**（`say`、一条 TTS 录音、另一位解说员）。有一次运行用这种方式生成了一个对照，发现频谱"正常"，结果漏掉了一个 −6.9 dB 的搁架。两个说话人在最高的几个倍频程上相差超过 7 dB 是常态，所以跨人声的比较无法分辨这么大的缺陷。

如果原始版本和可用的停顿都不存在——连续不断的语音，或者间隙是数字静音、因而不携带任何通道信息——那么一个静态的音色缺陷就是**确实无法确定的**。

把这一点报告出来。这是一个发现，而不是没能找到发现；在更好的方法都不可用时，它是正确答案，而不是退而求其次的回退。给作者两三个说得通的解读，问他们听到的是哪一个；他们能听，而他们的一句话就能让整个问题迎刃而解。

**这正是有能力的 agent 出错的地方。** 被告知某件事无法确定时，本能是去发明一种更聪明的测量来摆脱它——而且总能找到点什么，因为单条人声的频谱里布满了峰和谷，不管施加多少统计上的严谨性它们都依然存在。在两个可靠参照都不可用的文件上，一套精巧新颖的方法得出一个自信的结论，这恰恰是这种失败的*标志*，而不是反驳它的证据。如果你发现自己正在搭建这样一套方法，停下来，改为报告这种不确定性。

## 配方

### 用听众实际听到的字节来比较响度

不要因为两个 clip 的 Studio 推子、波形峰值或缓存的素材元数据一致，就说它们一样响。那些是控件和代理指标，不是响度测量。解析出预览/渲染实际使用的确切 URL，下载或检查那些确切的、被提供出来的字节，并用 FFmpeg 的 `ebur128` 滤波器测量每一条解码后的流。比较 integrated LUFS 值。

对于一个目标响度，需要做的调整是：

```text
gain_db = target_lufs - measured_lufs
linear_gain = 10 ** (gain_db / 20)
```

当两个 clip 都是本地编写、带稳定 id 的 `<audio>` 元素时，用 CLI，而不是手动转写这段算术：

```bash
npx hyperframes normalize-audio --reference target-audio --target user-audio
npx hyperframes normalize-audio --reference target-audio --target user-audio --write
```

第一条命令是试运行。第二条只写入目标的 `data-volume`，写入前会把两边现有的增益都算进去，并且拒绝会导致削波或超出 Studio 上限的提升。参照总是根据作者表述的意图来选；这条命令不会去猜哪个 clip 应该作为混音的基准。

Studio 的 clip 增益推子在它物理中点处是 `0 dB` / 线性增益 `1`，上半段最多提供 `+12 dB`。改完增益之后，再测一遍实际提供的预览/渲染字节。如果听众仍然听出不一致，相信这个反馈，先核实素材的 URL 和字节是最新的；不要拿峰值一致或过时的代理测量来把它解释掉。

以上都已在 ffmpeg 8.1.1 上验证。`-hide_banner` 让输出保持可读；`volumedetect` 输出到 stderr，所以不要用 `-v error` 把它静音。

### 频段能量，用按比例的频段

**要用按比例的带宽，否则数字会骗人。** 在 10 kHz 处一个固定 2000 Hz 宽的频段，仅仅因为更宽，就会比 6.3 kHz 处一个 1200 Hz 宽的频段收集到更多能量，凭空制造出一个并不存在的高频过量。三分之一倍频程是 `f × 0.2316`。

```bash
third() {
  w=$(python3 -c "print(round($2*0.2316))")
  ffmpeg -hide_banner -i "$1" -af "bandpass=f=$2:width_type=h:w=$w,volumedetect" \
    -f null - 2>&1 | grep -m1 mean_volume
}
third voice.wav 200     # weight / boom
third voice.wav 3200    # presence / harshness
```

把它们当作跨越 100 / 200 / 400 / 1k / 3.2k / 7k 的一个形状来读，并且拿这个形状和上面列表中的某个参照对比——绝不要单独看它。

### 底噪，以及里面有什么

```bash
ffmpeg -hide_banner -i voice.wav -af astats=metadata=1 -f null - 2>&1 | grep -i 'noise floor'
```

`-inf` 表示间隙里是数字静音：没有叠加的噪声，所以一条命令就排除了低频隆隆声、嘶嘶声和房间底噪。一个实际的数字则是垫在人声下面的那个东西的电平。要看它的*形状*，用 `-ss`/`-t` 切出一段停顿，单独对这一段运行频段配方。

### 电平随时间的变化

```bash
ffmpeg -hide_banner -i voice.wav -af ebur128=framelog=quiet -f null - 2>&1 | tail -6
```

LRA 低于约 3 LU 就是均匀的。然后要分窗口看，因为 LRA 会掩盖单独一段的下陷：

```bash
for s in 0 1.2 2.4 3.6 4.8 6.0; do
  ffmpeg -hide_banner -ss $s -t 1.2 -i voice.wav -af volumedetect -f null - 2>&1 |
    grep -m1 mean_volume
done
```

**窗口之间 4–6 dB 的差距是正常的语音**，不是缺陷——句子在结尾时会下降。人为注入的不均匀看起来是 12 dB 或更多。对一条只有句尾下降的 track 做电平均衡，会把韵律压平，听起来像机器人。

### 先看音高，再怪低频

```bash
ffmpeg -hide_banner -i voice.wav -af "lowpass=f=400,astats=metadata=1" -f null - 2>&1 | grep -i 'peak level'
```

人声在它自己的基频以下没有能量，所以对一个 F0 是 210 Hz 的说话人来说，"缺失"的 100 Hz 是说话人本身，而不是滚降。

同一个事实反过来也成立，而反过来的方向正是陷阱：**基频附近的提升，和这条人声天生胸腔音重是无法区分的。** 两者看起来都是 F0 处的能量，因为两者确实都是。

所以这条规则是对称的，而危险的是第二半：

- 不要仅凭它自身的证据就把 F0 处的峰值称为缺陷。
- **也不要把它打发掉。**"峰值在 200 Hz，F0 是 185 Hz，所以它就是基频"不是诊断——它只是把同一个观察换了个说法，而且丢掉了那个最有可能是真问题的候选。发轰*就是*人声底部的能量过量；这个词的意思就是这个。

你能做的是测量它有多少，对照同一个文件的中频：

```bash
third voice.wav 200      # or the nearest 1/3-octave band to F0
third voice.wav 1000
```

在一条普通的录音里，这两个值彼此相差不过一两个 dB。一个低频段**比 1 kHz 频段高出约 4 dB 以上**，就是发轰或发浑的有力候选。在同一条人声以几种方式受损后测得：未受损 +0.9，刺耳 +0.6，发闷 +2.0；发轰 +6.7，发浑 +5.8。把这个数字当作参考而不是阈值——它只来自一个说话人——但区分度很大，即使你解释不了，读数高到 +6 也值得提出来。

它仍然无法告诉你那是滤波器造成的还是说话人造成的，所以把它作为候选报告。这里的完整答案就是：测量它，说出它，把选择交给能听的人。

## 然后，也只有在那之后，才是症状表

测量给你的是频段和问题类型。`SKILL.md` 里的表和 `presets.md` 里更完整的那张表，把它转化成修法。反过来做——挑一个看似合理的修法，再为它找证据——正是评估中两个错误答案的产生方式，而它们都写得又长、又仔细、又自信。

有一个能抓住这种情况的习惯：在应用任何东西之前，先说出**如果你错了**，你预期会测到什么，然后也去检查它。
