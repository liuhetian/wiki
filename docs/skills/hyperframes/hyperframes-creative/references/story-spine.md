# 故事主干 —— 价值优先的叙事准则

适用于有旁白、由故事驱动的创作工作流 —— `/product-launch-video`、`/pr-to-video`、`/faceless-explainer`，以及作品要讲一个故事时的 `/general-video`。它**不**适用于 `/music-to-video`（音轨驱动弧线）、`/motion-graphics`（没有旁白 —— 运动本身就是信息）、`/embedded-captions` 和 `/talking-head-recut`（原片的故事已经定了），也不适用于 `/slideshow`（故事归演讲者掌控）。不要把这些规则强加给被豁免的工作流。

每个工作流自己的故事设计参考文档，掌管各自的原型、节拍序列和帧词汇。本文件掌管关于**顺序**和**理由**的四条跨工作流规则 —— 倒置冰山：先讲它为什么有价值，而不是先讲它是什么或怎么做出来的。

## 1. 钩子说观众的语言

第一拍用**结果语言**回答「我为什么要在乎」—— 观众能得到什么、避免什么，或者终于弄懂什么。钩子里禁用主题内部的词汇：代码变更的文件 / 函数 / API 名；产品的功能列表；讲解视频所依据文章的章节标题。数字只有在承载利害关系时才受欢迎（「冷启动快 40%」），绝不能是清点库存（「改动了 23 个文件」）。

## 2. 倒置冰山 —— 价值先于证据

价值主张（brief 的 `message`）**最迟在第二拍**落地。之后的一切都是为这个主张服务的证据 —— diff、机制、功能演示、网站截图。实现细节是故事的脚注，不是主干。

对完成的节拍清单做自检：

- 删掉所有证据拍 —— 剩下的拍子必须仍然能独立说清价值。
- 删掉价值拍 —— 如果视频似乎照样成立，那它就是一次功能巡览 / diff 宣读，而不是一个故事。

结构是价值优先的；**语气**仍然按工作流的规定（PR 视频保持它平实、不炒作的开发者语气 —— 先讲价值是一个排序决定，不是营销腔调）。

## 3. 分镜是一份提案，不是一张清单

当 Step 3 呈现计划时（一个检查点闸门 —— `hyperframes/references/brief-contract.md` § 1）：

- 开头复述策略句：**「这支视频告诉 [audience]：[message]。」**
- 把各帧以 markdown 表格呈现，每帧一行：

  | 帧            | 节拍      | 画面上                                               | 为什么                             |
  | ---------------- | --------- | ------------------------------------------------------- | ------------------------------- |
  | 01 —— 不再如此 | hook · 9s | 说出旧的痛点，并在同一口气里把它解决掉。 | 在第 1 拍落地价值主张 |

  **为什么**是这一帧在故事里的职责（来自它的 `narrativeRole`），并且要能追溯回 message —— 一个说不清「为什么」、追溯不到 message 的帧，应该删掉，而不是去装饰它。

- 推荐要附上依据（brief-contract § 3）：原型的选择、拍数，以及用户可能质疑的任何一拍，都各自说明理由。

分镜本身怎么写、用来审阅它的 `storyboard.html` 页面怎么做，见 `storyboard-recipe.md`。

提案的形态 —— 复述句 → 帧表格 → 风格 / 时长页脚 →「批准或调整」—— 是迭代成本最低的地方：在这里改一帧花 30 秒；搭建之后再做同样的改动要花好几分钟。

## 4. 画面要指回来源

当作品源自具体的来源材料时 —— 一个 PR、一个仓库、一篇文章、一个产品页 —— 在自己发明之前，先从这份材料里挖掘视觉词汇：它的措辞、实体、动词和反复出现的母题就是道具。每一帧的关键画面都应该能追溯到来源里具体的某一行，就像它的**为什么**能追溯到 message 一样：用真实的文件名，而不是通用的文件图标；用产品自己的数字，而不是编造的数字；用文章自己的隐喻，而不是现成的套路隐喻。

对每个画面自检：如果这个道具原封不动地出现在另一个产品的视频里也说得通，那它就不是来自来源。在装饰它之前，先把它换成只有这个主题才能产生的东西。
