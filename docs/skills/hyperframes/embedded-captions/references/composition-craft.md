# 构图工艺 —— 仅适用于嵌入轨

这是一份深入的"如何把字幕放**进**场景里"手册 —— 它只管**嵌入**轨（合成在主体身后的字幕）。默认的 **rail**（标准的 lower-third 字幕，大部分文字都在这里）有它自己的、简单得多的规范 → [rail.md](rail.md)。在编写任何**被提升**的短语之前先读这份文档，无论用哪种编写模式（模板 Cinematic 的 `plan.json`，或 Standard 的 `index.html`）。

主题：短语分组、plane 与干净区域锚定、区域一致性、高潮的冲击力、可读性、边缘留白、遮挡的三步判断、累积，以及持续时长。

> **双轨模型（SKILL.md § Caption model）。** 渲染状态是 `drop` / `rail` / `embed`。下文通篇使用的 `bg / fg / hybrid` 轴**已被取代**：把 **"bg" 读作嵌入**（在主体身后 / 在场景内），把 **"fg" 读作 rail 或向外提升**（在前面），把 "hybrid" 简单读作 rail + 嵌入共存。这里的一切都适用于**嵌入**轨 —— 不要把这套工艺用到 rail 上。

（更细的子主题也有各自的文件 —— 见 SKILL.md § Shared knowledge。）

### 字幕图层：BG vs FG（审美轴）

在选模板之外，还要单独决定字幕是**嵌入式**的（在主体身后，matte 遮挡 —— 默认的"嵌入"电影感），还是**宣告式**的（在主体前面，无遮挡 —— 海报 / lower-third 的感觉）：

- **bg** —— 经典嵌入。字幕位于 matte 之后，主体的身体会部分遮挡字母。**只要画面放得下，任何字幕都默认用它。** 部分遮挡正是电影感所在 —— 小号的 narrator 字幕被脸啃掉 20–30% 的字母，读起来就是嵌入的纹理；高潮词被脸横穿 30–40%，读起来就是 Vogue 刊头。正是这种"被吃掉"让嵌入成立。不要为了避开它而缩小字号。
- **fg** —— 字幕浮在最上层，主体无法遮挡。**是 bg 行不通时的兜底。** 两种情形：
  - **高潮 fg**：高潮词在有冲击力的字号下太大，主体加上画面宽度根本不给 bg 留任何渲染位置（主体占满画面，**并且**高潮短语很长；用 bg 的话会被吃到超出可读、直接变成破损）。
  - **全 fg 兜底**：少见，只在整个场景对任何字幕都没有可用 bg 区域时使用。
- **hybrid（混合）**（按分组的 `layer:` 字段）—— 当某一条字幕（通常是高潮）撞上了"没地方放 bg"的墙，而其他字幕（较小的正文字幕）用 bg 依然没问题时。**正文 bg + 高潮 fg** 是标准的 hybrid 模式。

**经验法则：**

- 小号的 narrator / 强调字幕：几乎总是 bg。主体吃掉几个字母边缘 = 嵌入的特色。
- 高潮：先试 bg，字号定到最大程度地横穿主体。如果这个字号放不进画面宽度，**并且**别处也没有干净区域，就用 fg。
- 不要把 hybrid 反过来：正文 fg + 高潮 bg 是**错误**的方向（牺牲了正文上轻松就能拿到的 bg 嵌入效果，同时把那个需要防止过度遮挡的高潮送进了火坑）。

**Hybrid 实例 —— Startup_Host（主体占满画面）。**

主体从上到下占满画面（head_top y=126 / 距顶部 10%）。正文字幕没有大块的干净区域，但放在上方两角的小号斜体 narrator 字幕会被主体吃掉约 25% —— 这正是嵌入的展示效果。高潮 "SUCCESSFUL STARTUP" 如果用最具电影感的字号走 bg，会被吃掉 40–50% 以上 → 越过电影感，变成破损。高潮走 fg。

```json
{
  "caption_layer": "bg",
  "groups": [
    {
      "id": "cg-0",
      "plane": "body",
      "layer": "bg",
      "css": "font-size: calc(0.055 * var(--h)); font-style: italic; ..."
    }, // narrator bg — face eats edges, embed texture
    {
      "id": "cg-1",
      "plane": "body",
      "layer": "bg",
      "css": "font-size: calc(0.085 * var(--h)); font-weight: 800; text-transform: uppercase; ..."
    }, // emphasis bg — Vogue masthead
    {
      "id": "cg-5",
      "plane": "crown",
      "layer": "fg",
      "css": "font-size: calc(0.09 * var(--h)); font-weight: 900; text-transform: uppercase; ..."
    }
    // ↑ climax fg: subject too dense for bg to land readably; fg fallback. Sized to fit frame width fully (single line).
  ]
}
```

结果：正文 bg 在主体身上做出了嵌入的电影感（被吃掉的边缘 = 纹理，不是 bug），高潮 fg 完整可见地浮在最上层，因为它没有别的地方可去。make-composition.cjs 会同时输出 `index.html`（bg 分组）和 `index_fg.html`（fg 分组）；render-and-composite.sh 并行跑两遍 Chromium，再由 ffmpeg 把 fg 以 screen 混合叠到 bg+matte 之上。

在 plan 层级通过 `caption_layer: "bg" | "fg"` 设置（作为没有显式 `layer:` 的分组的默认值），并在分组层级用 `layer: "bg" | "fg"` 覆盖，以实现 hybrid。

**决策规则 —— bg 是默认，fg 是兜底，hybrid 用于语义混合的内容。**

对**正文**字幕（narrator + emphasis）：

1. **找到真正的干净区域。** 在 20/50/80% 处采样帧，在脑子里描出主体所在的位置（头、肩、做手势的手）。剩下的就是干净区域。头顶上方的横带、肩膀下方的横带，或者偏离中心的侧栏。
2. **把 plane 锚定在那个区域里。** 正文字幕能舒服地放下且**不**与主体重叠 → `layer: "bg"`。
3. **如果正文字幕堆叠本身就和主体严重重叠（按 check-occlusion 的峰值 >40%）**，即使用最小的合理字号也是如此 → 正文 `layer: "fg"`。主体占画面太多，无法嵌入。

对**高潮**字幕（落点）：

1. **默认：`layer: "bg"`，字号定到最大程度地横穿主体以获得嵌入效果。** 脸 / 身体吃掉高潮词的一部分，**正是**视觉上的胜利。不要为了避开遮挡而缩小。使用能放进画面**宽度**的最大字号（字母清晰可读、完全在画面内）—— 垂直位置应让它横跨主体的头发 / 额头 / 脸。
2. 高潮**只有**在以下情况才用 **`layer: "fg"`**：画面宽度在物理上放不下一个大到足以有高潮感的字号，**并且**在构图上也没有办法把这个词拆成多行、让 bg 嵌入撑得住。
3. **Hybrid（正文 bg + 高潮 fg）** 是主体占满画面场景的标准模式。正文小字幕保持 bg —— 主体吃掉字母边缘 = 嵌入纹理（有电影感，不是 bug）。高潮走 fg，**仅仅**是因为在有冲击力的字号 + 主体占满画面的条件下，bg 高潮找不到能读得清的落点（会被吃掉 50% 以上 = 越过电影感变成破损）。反方向（正文 fg + 高潮 bg）牺牲了小字幕上轻松就能拿到的 bg 嵌入效果，还把高潮逼进一个它活不下来的位置 —— 绝不要这么做。

**编辑式分屏 —— 正文 bg + 高潮 fg 的空间形态。** 当上面这种 hybrid 按**bg 在上半部、fg 在 lower-third** 来布局时，你就白捡了一个杂志封面式构图 —— 不需要单独的模板。规则：

- **正文字幕（BG）** —— 放在上半部（top: 6–30%），头部 / 头发区域。它们会被头发 / 额头部分遮挡 = Vogue 刊头式的嵌入纹理。
- **高潮字幕（FG）** —— 放在 lower-third（top: 70–85%），在主体胸部前方 / 下方。完全清晰、完全可读，主导底部横带。

观众的视线从上往下读：先是被部分遮住的正文行（"装饰性的、营造氛围的"），然后是干净的高潮陈述（"重点"）。和 Vogue / Apple Keynote 一样的 Z 轴分层（装饰性的上部在主体身后 + 清晰的底部在主体前面），但它是靠 cinematic-cream 现成的按字幕 `layer:` 字段驱动的 —— 不需要新模板，也不需要单独的刊头轨。

这种布局内部有两种时间模式：

- **依次交叉淡化（默认）** —— 正文在 0.3–0.5 秒内淡出，同时高潮淡入。这段短暂的重叠窗口**就是**编辑式双层的那一刻。cinematic-cream 的标准行为。
- **持续重叠** —— 把正文的 `out` 延长到与高潮的 `in` 重合或超过它，让两者一起可见 1–2 秒。要节制使用：适用于正文行很短（≤3 个词）、在高潮上方充当"引子"的情况。长的正文短语和 fg 高潮一起长时间停留 = 视觉噪音。

**持续重叠的 plane 冲突规则（在 Startup_Host 中调试出来的）。** 如果你把一条正文 bg 字幕的 `out` 延长到一个时间窗口里，而这个窗口中有另一条**同一个 plane 里**的 `layer: "fg"` 字幕，两者就会在最终合成里视觉重叠 —— bg 那一遍渲染被延长的 bg 字幕，fg 那一遍渲染 fg 字幕，两者在完全相同的 plane 位置上，用 screen 混合叠在一起。结果：同一位置出现浑浊的重影文字。

在延长任何正文 bg 的 `out` 之前：

1. 检查延长的窗口内还有哪些字幕占用正文 plane
2. 只要其中**任何一条**是 `layer: "fg"`，延长就会造成 plane 重叠 → 不要这么做
3. 变通办法：要么 (a) 放弃持续重叠，只用依次交叉淡化；要么 (b) 把正文引子写到一个**不同的** plane / 绝对位置上，让两者不共用一个 plane

具体例子：Startup_Host 有 cg-3 "diving deep"（正文 bg，plane=body，3.1–4.15 秒）和 cg-4 "into what it really takes to build a"（正文 fg 兜底，plane=body，4.15–6.42 秒）。两者都占用 `plane=body`。把 cg-3 延长到与高潮 cg-5（6.42–8.06 秒）重叠，**也**会把 cg-3 拖过 cg-4 的窗口，在那里 cg-3（bg）和 cg-4（fg）在正文 plane 上相撞。依次进行的编辑式分屏（高潮在 lower-third，正文 bg 已经淡出）是这个案例唯一安全的选择。AI_Insights 在引子和高潮之间的正文 plane 上没有 fg，所以持续重叠在那里行得通。

什么时候**不要**用编辑式分屏：

- 正文和高潮都是承载信息的完整句子 → 逼着观众同时读两句，失败。编辑式分屏需要正文行是*营造氛围 / 铺垫*（斜体的情绪），高潮是*落点*（粗体全大写）。
- 主体占据整个垂直方向（顶部没有干净区域，底部也没有）→ 没有上方或下方的横带来锚定任何一层。退回到全 fg 加 crown。
- 高潮是一个长短语，在 lower-third 里折成 3 行以上 → 吃掉太多垂直空间，上方没地方放正文 bg。要么缩小高潮，要么拆成更多分组。

这个模式历史上被我们叫作 "hybrid"，但真正让它读起来像编辑设计、而不只是两条互不相关的字幕轨的，是它的空间框架 —— 上方 bg 在后 / 下方 fg 在前。为 hybrid 场景编写按字幕的 `layer:` 时要记住这一点。

常见错误（在真实案例中调试出来的）：

- 因为 memory-wall 这么做过，就默认用"右侧栏" → 400px 的窄栏迫使长短语折成 4–5 行，把整个堆叠往**下**推进主体的身体。修正：改用顶部全宽横带，更宽的换行宽度能少折几行。
- **因为"观众需要读到它"就把高潮翻成 fg → 毁掉了电影感的嵌入。** 高潮本来就应该感觉被主体吃掉了一半；那就是杂志刊头的气场。没坏的东西不要修。
- 主体占满画面时整个 plan 全用 fg → 安全但乏味。Hybrid（正文 bg + 高潮 fg）几乎总是更好 —— 小号正文字幕被吃 = 嵌入纹理，高潮完全可见，因为它没有可读的 bg 位置。
- 先定字幕字号再选 plane → 字体排印是 plane 几何形状的函数，而不是反过来。
- **在主体占满画面的场景里把多行的长短语放在 bg 上。** "主体吃掉字母边缘 = 嵌入纹理"只对短字幕（1–3 个词 / 1 行）成立。一个 6–8 个词的斜体短语会折成 3–4 行，当主体的头在画面里位置较高时，短语的**整行**会深深落进身体 / 脸部区域 —— 整个词被抹掉，而不是边缘纹理。那不是嵌入，是破损。**对主体密集场景里的长正文短语：把那一条字幕单独切到 `layer: "fg"`，即使其他正文字幕保持 bg。** Hybrid 允许你按字幕混用。在该字幕的时间窗口内采样 matte：如果 head_top 的 y 在往上爬，而字幕堆叠的高度延伸到 y > head_top，这条字幕就需要 fg。
- **主体在整个片段里并不是匀速移动的 —— 要按每个块（BLOCK）的时间窗口采样 matte，而不是每个案例只采一次。** Startup_Host 的 head_top 在 8 秒内从 y=224 摆到 96（128px / 画面的 10%）。一个在 t=2 时可行的块方案（头低，空间充足）到 t=5 就失效了（头高，没空间了）。按块采样 matte > 每个案例一次性采样。

### 任何 plan 的 Step 0 —— 转写稿角色标注（必做）

在写下任何一个字幕分组之前，先对转写稿做一遍**规划前的 agent 式处理**。读每一个词并给它评级。这是判断，不是查表 —— 由上下文决定（例如 "like" 在 "like this" 里是内容，在 "like, um, yeah" 里是填充词）。没有硬编码的词表；agent 按每个 token 判断。

**评级是选择的输入 —— 它决定渲染状态**（`drop` / `rail` / `embed`）；它本身不是一个字体排印类（见 SKILL.md § Caption model）：

| 评级        | 是什么                                                                                                                                               | → 渲染状态                                                                                    |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **drop**     | 感叹词 / 迟疑（um、uh、er、ah），自我更正（"I think— I mean actually…" 只保留最后一句），纯结巴（"the the the"）合并成一个 | **drop**（不显示）                                                                              |
| **normal**   | 普通的口语内容 —— 起连接作用的词 + 承载意思的实词                                                                        | **rail**（密集的口语连接词可以为了可读性修剪；实词 / 结构词保留） |
| **emphasis** | 一个短语里那 1–2 个有冲击力的词                                                                                                                          | **rail** + `emphasis` 高亮（行内 —— 留在 rail 上）                                      |
| **peak**     | 一个段落节拍 / 一个章节的落点 —— 你转述它时会大声说出来的那一句                                                                               | **提升为嵌入**（应用下面的工艺）；整部作品中最大的那一个 = `apex`      |

**peak** 是按段落节拍算的，**不是**按片段算的：一个短片段通常只有一个（它的高潮）；一个长的 / 多章节的讲解视频大约每个章节一个。**嵌入是稀缺且要拉开间距的** —— 每句话 / 每个段落节拍最多 1 个，绝不两个相邻或同时可见，至少间隔一拍，`apex` 最多一个。（旧的"每个 10–20 秒片段 1 个高潮 / 2–4 个强调 / 4–10 个正文 / 6–12 个 narrator / 2–8 个 drop"是针对单段落节拍的短片段校准的；推广开来就是"每个段落节拍一个 peak，拉开间距 —— 其余全走 rail"。）

**这一步取代任何填充词列表。** 如果你发现自己在伸手写正则，那就做错了 —— 回去逐个 token 判断。

然后根据标注好的词构建 plan：

- drop → 不出现在任何词条目里
- narrator → 要么并入相邻的正文分组，要么在节奏需要时成为小号斜体的从属分组
- 正文 / 强调 / 高潮 → 塑造分组结构，字体排印与角色相匹配

### 构图单位是短语，不是碎块（这一节读两遍）

一个**字幕分组**是一个语义短语 —— 通常是 2–8 个由语调和意思绑定在一起的词。它**不是**一个机械的"2–4 词碎块"。一个分组只有**一种**字体排印（一个字号、一个字重、一种大小写、一个位置），与它的角色相匹配；"每个词都有"的感觉来自**分组内部的逐词 GSAP stagger**，而不是把短语拆成许多很小的分组。

标准参考 —— memory-wall，12 个口语词，**4 个分组**：

- cg-0 `"Some memories feel soft"`（4 个词，斜体 600，右上）
- cg-1 `"like old film"`（3 个词，斜体 500，右中，更小）
- cg-2 `"but suddenly"`（2 个词，正体 700 支点，右侧居中）
- cg-3 `"EVERYTHING IS SHARP AGAIN"`（4 个词，全大写 900 高潮，横跨宽度）

每个词都会显示。分组**层叠并累积** —— cg-1 在下方入场时 cg-0 仍留在屏幕上；到高潮时，4 个分组同时可见，像一首诗。逐词 stagger（约 80ms）让每个词依次动画进入它的分组。

如果你发现自己为一个 10 秒的片段做出了 15 个以上的分组，停下 —— 你把逐字当成了机械切块。回去重读转写稿，找出 4–7 个短语，把它们做成分组。

**不要把习语、固定搭配或粘连短语拆到不同分组里。** "Not even kidding"、"at the end of the day"、"as a matter of fact"、"whole lot of"、"more or less"、"a little bit"、"kind of"、"sort of"、专有名词（"Blackmagic Pocket 4K"）、品牌短语以及其他固定表达都是语义单元。"I'm not even kidding" 的高潮是整个习语，而不只是 "KIDDING"。memory-wall 标准范例的高潮是作为一个分组的 "EVERYTHING IS SHARP AGAIN"，而不只是 "AGAIN"。把这些拆到分组边界两侧，既破坏意思**又**破坏字体排印（你没法把 "not even kidding" 渲染成 "not even" 用小号斜体、"kidding" 用巨大全大写 —— 那读起来像两个不同的陈述）。

### 字幕永远逐字

说话人说的每个词都要上字幕。这个 skill 不再提供"highlight"模式 —— 经过挑选 / 编辑的转写稿产生的段落节拍更少，却丢失了口语句子的节奏，最后感觉就像普通的字幕轨。逐字加上强烈的字体排印层级（小号斜体 narrator → 正体强调 → 巨大的全大写高潮），能在不丢内容的前提下给出电影感。

你只从转写稿里删掉这些词：

1. **纯语音感叹词**（um、uh、er、ah、hmm）—— 不是词，不上字幕。
2. **完全相同的紧邻结巴**（"the the the" → 保留一个；"is is is is" → 保留一个，与后面的短语对齐）。观众应该看到一个 "the"，而不是三个。
3. **自我更正的回退**（"I think— I mean actually…" → 只保留 "I mean actually"）。

**所有实词和结构词都保留**（冠词、连词、介词、助动词、代词）。删掉像 "in some"、"and I've" 或 "out of it" 这样的结构词是 bug，不是风格选择。

### Plane —— 用于空间一致性的共享父容器（推荐）

memory-wall 和 champion 这两个标准范例并没有给每条字幕设 `top:`。它们有一个**父容器**（`wall-plane` / `left-plane` / `crown-plane`）来掌管空间锚点，字幕是它的子元素，自动堆叠（带 gap 的 flex 列）或替换（在同一锚点绝对定位）。

你的 plan.json 可以通过声明 `planes` 并把每个分组分配给其中一个来启用这种方式：

```json
{
  "planes": {
    "body": {
      "css": "top: 4%; right: 4%; width: 720px; display: flex; flex-direction: column; align-items: flex-end; gap: 14px;"
    },
    "crown": {
      "css": "top: 32%; left: 0; right: 0; text-align: center;"
    }
  },
  "groups": [
    { "id": "cg-0", "plane": "body",  "css": "font-size: calc(0.08*var(--h)); font-weight: 600; font-style: italic;", ... },
    { "id": "cg-1", "plane": "body",  "css": "font-size: calc(0.10*var(--h)); font-weight: 800;", ... },
    { "id": "cg-2", "plane": "crown", "css": "font-size: calc(0.20*var(--h)); font-weight: 900; text-transform: uppercase;", ... }
  ]
}
```

plane 的 CSS 掌管定位（top/left/right + display:flex/grid/block）。分组的 CSS **只**掌管字体排印（font-size、字重、样式、大小写、letter-spacing、line-height）。**分组在 plane 内时，不要给它设 top/left/right/position** —— 由父容器决定。

**字体排印由 agent 按分组编写，不是从 preset 里查出来的。** `cinematic-cream` 模板只锁定 DNA（Inter 字体家族、动效曲线、`mix-blend-mode`、`cap_color` 色板、由亮度推导出的 text-shadow/filter）。其余一切 —— `font-size`、`font-weight`、`font-style`（斜体 vs 正体）、`text-transform`（全大写 vs 大小写混排）、`letter-spacing`、`line-height` —— 都由 agent 按分组写在 `plan.json` 的 `css` 字段里。没有"cap-1 必须是斜体 600，cap-2 必须是全大写 900"这种规则。读场景 + 转写稿，挑选与语义角色（narrator/正文/强调/高潮）以及画面能承载的视觉分量相匹配的字体排印。*推荐的*组合见 [references/typographic-moves.md](typographic-moves.md) —— 把它当色板，而不是模式定义。

什么时候用 plane：

- **一个多短语的句子放在一个大本营区域里** —— 用 flex 列 plane。里面所有正文字幕自动累积 / 堆叠，不用算碰撞。这就是 memory-wall 模式。
- **正文区域 + 高潮区域** —— 两个 plane：body（flex 堆叠）+ crown（居中）。正文字幕住在 body plane 里；高潮在 crown plane 里跳出来。跨 plane 的转换 = 挣来的断点。
- **任何有 ≥3 个正文短语的片段** —— 单 plane 的 flex 堆叠每次都胜过手动摆放每个分组的 top%。

### 选择 plane 锚点 —— 在**这个**场景里找到**真正的**干净区域

**不要因为 memory-wall 用了"右侧栏"就默认用它。** memory-wall 行得通，是因为它的主体坐在偏左居中的位置，右边是一面干净的墙。不同的场景有不同的干净区域：

- **主体居中（大多数自拍、vlog）** → 头顶上方的横带通常最干净（晴朗的天空 / 天花板 / 墙面）。左右侧栏会被肩膀或手吃掉。
- **主体在左（背景是右侧栏的访谈）** → 右侧栏瀑布式排列（memory-wall 经典）。
- **主体在右（反向访谈）** → 左侧栏瀑布式排列。
- **双人镜头或繁杂背景** → 可能需要用一个角落，或者把字幕放在**唯一**一块始终干净的表面上（纯色夹克、白板、天花板）。

写 plane 的 CSS 之前，先看一帧采样画面。在脑子里描出主体的包围框和手势可达范围。plane 锚定在**剩下**的地方 —— 瀑布式文字不会被身体或繁杂背景吃掉的负空间。

小号斜体的 narrator 文字尤其脆弱 —— 它会消失在斑驳的背景里或被身体遮挡。把最小的字幕放在区域里最干净的部分，而不是主体会伸展到的边缘。

什么时候**不**用 plane（剩下的自由模式用例）：

- **1–2 个孤立的分组**，故意放在不同位置 —— 自由模式更简单。
- **贯穿片段的特定运动**，某个分组需要独立漂移 / 移动。

自由模式（不声明 `planes`）仍然受支持 —— 每个分组的 CSS 掌管自己的 top/left/right。在你确实需要按分组定制摆放时使用。

错误："9:16 的主位是 top:12%"。那是查表；产出的是平庸的结果。正确：看**这个**场景，找到字幕能读得清的地方，尊重说话人的构图，挑一个服务于内容叙事弧线的构图模式。

agent 可以挑选的模式示例（不完整，也不分先后）：

- **右侧瀑布式累积**（memory-wall）：所有分组右对齐，top% 逐级下移，它们都留在屏幕上 —— 最后一帧呈现一首诗。适用于主体居中偏左、右侧栏有干净空间的情况。
- **居中堆叠高潮**（Sunset）：斜体开场在顶部，正体支点在中间，全大写高潮作为最后一拍占满整个顶部，之前的分组在高潮前淡出。适用于主体居中、场景有干净天空 + 肩膀下方干净的情况。
- **左右分屏**（memory-wall 变体）：narrator 的声音在一侧用斜体，陈述的声音在另一侧用正体，高潮占据中央。适用于主体两侧有偏离中心的干净区域的情况。
- **单行字幕 rail**：当场景密集、没有干净区域时（繁杂背景、主体占满画面），这是合理的选择。这是"无障碍"兜底，不是默认。

无论挑了哪个模式，agent 的任务都是**给出选择的理由**："主体在左，右边是干净的渐变天空 —— 我会做右对齐瀑布式排列，让字幕全程都有干净的背景。"把这段推理写成 plan.json 里的 `_notes` 字段，让意图可以被检查。

**绝不**交付的反模式：

- 每个碎块在顶部↔底部之间交替 —— 读起来一片混乱（一句话的词出现在不同的垂直区域）。
- 把每个分组都锁定在相同的 `top` 值 —— 读起来像字幕轨，毁掉电影感。
- 明明有干净空间，却把正文 / narrator 分组直接放在脸上 —— Vogue 式嵌入效果只用于**高潮**词，不是默认行为。
- **为了把字幕塞进更少的块而删掉转写稿里的词。** **绝不。** 逐字就是逐字。如果 4 条字幕放不进 1 个块，就拆成 2 个子块、每块 2 条 —— 保留所有词。唯一合法的删除是 SKILL.md 的填充词列表（um/uh/完全相同的结巴/自我更正），而不是"我们没地方了"。
- **机械地让一个 plane 里所有字幕共享同一个 `out` 时间。** 这会让所有字幕在屏幕上停留得更久，*增加*密度。这是对"不跳动"问题的错误修法。正确修法：把自然交接的字幕拆成独立的块，每个块里的字幕共享 `out`（同一时刻退场，不跳动），并且 `next_block.in ≥ prev_block.out`（块与块之间干净交接，没有重叠）。

**块边界三定律**（每个 plan 的每个 plane 都必须满足）：

1. 一个块内，所有字幕共享 `out` —— 它们一起淡出，没有逐条退场的抖动。
2. 同一 plane 中相邻的块之间，`next_block.in == prev_block.out`（或者 `next.in > prev.out`，留一个小间隔）。prev_block 的字幕必须**完全**退场后，next_block 的字幕才能挂载；否则 prev 字幕在其 `out` 时刻的退场会触发一次 flex 重排，把 next_block 已经挂载的字幕往上猛拽 = 跳动。
3. `prev_block.out ≤ next_block.first_word.start`，这样 next_block 的第一个词仍然从它真实的说出时间开始动画（in 时间只约束容器何时挂载；词动画在各自的 `start` 触发）。

一个常见错误：把 `next_block.in` 设得比 `prev_block.out` 稍**早**一点，好让新块提前开始淡入，而 prev_block 还有一个不同的（更晚的）`out`。50–300ms 的重叠在 plan 里看不出来，但在屏幕上会产生明显的跳动，因为两条 `out` 不同的字幕共存于同一个 flex 堆叠中。

- **正文底部和 crown 顶部之间的垂直空隙。** 看起来是断开的（"The pace is" 在 top:3%，"UNPRECEDENTED" 在 top:20%，中间形成 144px 的空洞）。通过 flex 堆叠把铺垫短语 + 高潮词绑在**同一个** crown plane 里 —— 即 Street_Talk 的 "and being / CONSISTENT" 模式。

### 区域一致性 —— 一句话，一个大本营区域

**绝不在一句话中途切换空间区域。** 一个完整的语义单元（句子或分句）应该住在**一个**大本营区域里（例如右侧栏，或顶部横带）。观众的视线追随短语分组。同一句话的相邻短语在上 / 下 / 左 / 右之间来回跳，读起来一片混乱 —— 读者每一拍都得重新找字幕。

区域切换要在这些地方才算挣来的：

- **句子边界**（句号、长停顿、话题转换）—— 可以移到一个新的大本营区域，通常伴随语气转换（斜体正文 → 全大写强调）
- **唯一的高潮** —— 唯一一次脱离大本营区域，永远允许，通常占据居中的全宽

经验判断：如果你发现 cg-N 和 cg-N+1 在不同区域（上 vs 下，左 vs 右），**并且**它们是同一句话的组成部分（之间没有句号 / 长停顿），你就违反了区域一致性。修正方法：为整句话挑一个大本营区域。

### 高潮必须跳出来 —— 不只是"稍微大一点"

一条和正文强调一样大的高潮字幕，就是一个失败的高潮。观众的视线需要一个清晰的视觉断点：**这**就是落点。

**嵌入式高潮的字号按画面定，而不是按 rail 定（双轨规则）。** 高潮是一个 hero —— 它的字号锚定在画面高度上：**`font-size: calc(0.16–0.22 * var(--h))`**（默认约 0.18–0.20h；想要更强冲击力就再大一些 —— 它应该主导画面，只有宽度 / 可读性给它封顶）。它**不是** rail 的倍数：rail 是一条小号的标准字幕（约 0.045h），所以"≥ rail 的 1.8 倍"只会得到一个又小又弱的高潮。把 rail、嵌入正文和嵌入高潮都表达成 `var(--h)` 的分数，这样它们能在不同分辨率间缩放 —— **绝不硬编码 px**。下面的比例是一个**下限 / 层级检查**（高潮必须比正文强调大 ≥1.8 倍，比最小一档大 ≥2.5 倍），不是高潮的字号依据。宽度才是真正的天花板：只有当这个词在清晰可读的字号下放不进画面时才缩小（见"可读性是硬约束"）。

对比下限 —— 高潮至少要越过这些：

| 比例                      | 感觉像                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| **正文强调的 1.0–1.3 倍** | 平 —— 高潮只是又一个段落节拍。修掉它。                                             |
| **正文强调的 1.5–1.8 倍** | 看得出来，但不够爆。对含蓄的落点可以，对点睛之句太弱。                   |
| **≥ 正文强调的 1.8 倍**    | 跳出来了。观众视线会被它一把抓过去。"点睛之句" / "揭晓" / "反应"类高潮的目标值。    |
| **≥ 正文斜体的 2.5 倍**      | 也要和**最小**的正文档位比较 —— 跨越多个档位的跳跃才是层级感的来源。 |

一个快速审计脚本 —— 交付之前，把每个 plan 的最大正文字号与最大 crown 字号之比导出来，标记出任何 <1.8 倍的：

```js
const bodyMax = Math.max(...plan.groups.filter((g) => g.plane === "body").map(fsize));
const crownMax = Math.max(...plan.groups.filter((g) => g.plane === "crown").map(fsize));
const ratio = crownMax / bodyMax; // aim for ≥1.8
```

**拆分模式 —— 当一个词应该独自扛起高潮时。** 如果高潮短语有 2 个以上的词（"and being consistent"、"not even kidding"），而其中一个才是真正的落点，就拆成铺垫 + 落点，**但**要让它们在空间上绑在一起：

- 铺垫词 → 第 1 行，小号斜体 narrator（轻柔、渐弱）
- 落点词 → 第 2 行，巨大的全大写，同一个 plane，用 flex 直接堆叠在下方
- **两个分组住在同一个（crown）plane 里**，flex 列，gap 4–8px。不是两个不同的 plane —— 否则 "and being" 坐在顶部横带，"CONSISTENT" 坐在画面中部，读起来就像两条不相关的字幕。

拆分高潮用的 crown plane CSS：

```
"crown": "top: 26%; left: 0; right: 0; display: flex; flex-direction: column; align-items: center; text-align: center; gap: 6px;"
```

Street_Talk 标准范例：原本是 `"AND BEING CONSISTENT"` 全部放在 crown 里，字号 0.085h（和正文强调一样，比例 1.0 倍）。改写后：crown plane 变成 flex 列；`"and being"` → 0.055h 斜体，放在列顶部（第 1 行）；`"CONSISTENT"` → 0.11h 900 全大写，堆叠在下方（第 2 行）。落点之所以能跳出来，是因为在一个绑定的 2 行构图内部有字号对比，**而且**因为 crown 列锚定在 top 约 26–30% 处，它横穿了主体的头部。

时间点：两个分组共享 `out`（在片段结尾或块边界），这样哪个都不会单独淡出 —— 它们作为一个整体构图一起停留。铺垫先入场（柔和淡入），落点在这个词被说出时再入场（更利落的 present 缩放入场）。

**可读性是硬约束 —— 出血不能吃掉这个词。** 当高潮词溢出时，你的第一反应**不是**"接受出血，这很电影感"—— 而是"缩到放得下的最大字号"。计算放得进画面的最大字号：

```
max_font_px = frame_width / (chars × char_ratio × letter_spacing_mult)
```

以 "CONSISTENT"（10 个字符）为例，全大写 900（char_ratio 0.62），letter-spacing -0.05em（倍数 0.95），720px 画面：`max = 720/(10*0.62*0.95) = 122px ≈ 0.095h`。用 0.09h 留一点安全余量。这个词从左到右完全占满画面 —— 这已经是不丢任何字母的最大视觉冲击了。

电影感的出血只有在这种情况下才可以：外侧 1–2 个字母因缩放入场动画或亚像素取整而被**轻微裁掉几个像素** —— 那读起来是"比画面还大"。任何迫使读者在脑子里补全缺失字母的出血（10 字符的词每侧 >15–20px）都是 bug，不是风格。每侧被裁掉 80px 的 "ONSISTE" **不是**有效的高潮 —— 它是破损的。

硬性规则：

- **可读第一。** 每个字母都应完整在画面内，最多第一个 / 最后一个字母被裁几个像素。
- **如果最大可读字号达不到比例目标**，就用*其他*信号提升冲击力（字重 900、全大写、bg 横穿头部、上方带铺垫词的多行构图），而不是靠不可读的出血。
- **绝不让正文 / narrator 字幕出血。** 只有 crown / 高潮才允许有任何边缘裁切。
- `OCCLUSION_SKIP=1` 是迭代时用的逃生口；交付的 plan 应该通过 `check-occlusion-v2.py --strict`（通过 headless Chromium DOM 做到像素级精确）。

### 边缘留白 + 高潮横穿头部（bg 展示）

两个摆放上的微调，区分"看起来像一条坐在场景里的字幕"和"看起来像一条贴上去的字幕"：

- **非高潮字幕需要边缘留白。** body plane 的分组**不应该**用 `left: 0; right: 0` 紧贴画面边缘。加上 `left: 3-6%; right: 3-6%`（像素锚定的 plane 则用 `right: 30-40px`）。留白体现的是构图上的选择 —— 紧贴边缘读起来像"默认字幕轨"，缩进的边缘读起来像"深思熟虑的构图"。顶部边缘同理：用 `top: 2-6%`，不用 `top: 0`。

- **高潮应该横穿主体头部的一部分 —— 是刻意为之。** 正是这一点让 bg 图层字幕有电影感，而不只是"浮在说话人上方的文字"。当词的最后一行有 20–40px 沉到头发或额头后面时，效果最强 —— 观众能清楚读到这个词，**同时**看到它在边缘被遮挡。不是"被脸盖住"（读不了），只是"被头发擦过"（可读 + 电影感）。

  如何有意图地摆放 crown：
  1. 在高潮时间点采样 matte PNG：`f_{frame_idx:04d}.png`，其中 `frame_idx = round(climax_time * fps)`。
  2. 从顶部逐行扫描，直到 `alpha > 128` —— 那个 y 就是主体最顶端的像素（通常是头发）。
  3. 摆放 crown，让*最后一行的底部*落在那个 y 下方 30–80px 处。对于一个在 1290h 画面上字号 0.085h 的 2 行 crown，每行行高约 104px；总高约 200px。如果主体顶部在 y=445，就设定 `crown.top` 使 `top + height = 445 + 50 ≈ 495` → `top = 295px ≈ 23%`。
  4. 用检查器验证 —— HERO/crown 的峰值遮挡目标约为 30–55%（嵌入效果；头部从中间横穿）。低于约 15% 读起来像一个漂浮的标签（会触发 hero-weak 提示）；高于约 65% 这个词就被吃掉了（闸门 FAIL）。小号 narrator 字幕：约 20–30% 的纹理。

  实用经验法则：**crown 峰值遮挡 3–10%** 是最佳区间。检查器的数字会直接告诉你 —— 而不是主观的"看起来不错"判断。

  **crown 的默认值是按场景定的，不是模板通用的。** 不要因为"上一个案例就是这么用的"就设 `crown.top: 6%`。如果主体的 head_top 在 y=380（画面的 29%），而你的 crown 在 top:6%、高 100px，crown 底部就落在 y=200 —— 在头顶**上方** 180px，完全漂在天空里，零嵌入效果。每个案例都要采样一次 matte，并按 `head_top - crown_height + (30 to 80)` 计算 `crown.top`，让 crown 的底边沉进头发里。在强制执行之前，这是一个横跨 6 个案例的真实 bug。

  FG 图层的 crown 完全跳过这一步（它们渲染在最上层，没有可展示的遮挡）—— FG 是宣告，不是嵌入。

### 渲染前的遮挡 + 画面溢出闸门

**`check-occlusion.cjs`（标准、像素级精确）** 是 `scripts/` 里唯一的遮挡检查器。它会自动运行 `measure-layout.cjs`（通过 Puppeteer 驱动 headless Chromium），加载编译好的 `index.html`，把 GSAP timeline seek 到每个分组的 4 个采样时间点（窗口的 15/40/65/90% 处），并对每个 `.cap` 和子 `.w` span 查询 `getBoundingClientRect()`。输出是 `_layout.json`，包含每个词在每个采样点实际渲染出的像素坐标。然后它对照真实的主体 matte alpha（通过 `sharp` 读取）计算逐词、逐字幕的遮挡：

- **逐词峰值遮挡** —— 起决定作用的指标：一个 5 词短语里有 3 个词被完全吃掉，平均值和 8 个词各被吃掉一半是一样的，但只有其中一种能交付，所以起闸门作用的是逐**词**峰值。逐词峰值 ≥65% = `obliterated`，≥35% = `warn`。单个高潮词落进 `WARN` 区间是可以的（电影感的边缘裁切）；两个相邻的词被抹掉则不行。
- **逐字幕汇总** —— 所有采样点上的平均 + 峰值遮挡。字幕在峰值 ≥50% 时失败。
- **fg 图层字幕会被自动跳过**（它们渲染在 matte 之上；不可能被遮挡）。

**为什么要测量真实 DOM，而不是估算包围框。** 早期的一个启发式方法根据 `char_ratio × font × text_length` 估算每个词的框，结果两个方向都错。Startup_Host 案例：它报告 `cg-1 "podcast." OK at 9%/12%`，因为它猜 y=134（在主体头顶上方），但渲染出的 DOM 在 y=209（头部中间）→ 实际是 `FAIL 54%/60%`。同一个案例，它报告 `cg-3 "diving deep" FAIL at 76%/77%`，而真实测量是 `WARN 36%/40%`（框比头宽 —— 大部分像素是空的，只有下伸部分沉进了轮廓）。估算已退役；`check-occlusion.cjs` 测量的是渲染出的像素。

**画面边缘溢出** —— 检查器还会在测得的词包围框超出画布时标记出来（即会被 ffmpeg 裁切掉的文字），报告格式为 `cg-N  [overflow] "word" off-frame: left Xpx, right Ypx (@Ts)`。因为被裁切的正文文字永远是错的，明显的字形裁切（超出边缘 >8px）会**让 `--strict` 失败**；不足一个字形的擦边（≤8px —— 高潮被允许的首 / 尾字母裁切）则是不阻塞的 `[overflow-warn]`。

**检查器报告事实，agent 做判断。** FAIL **不是**自动的"必须重新布局"信号 —— 它是需要解读的证据。两个相互竞争的目标同时存在：

1. **可读性** —— 每句话都必须让观众能理解
2. **电影感嵌入** —— 部分遮挡正是想要的 Vogue 刊头效果；零遮挡看起来像贴上去的字幕

当检查器报告某个词被抹掉（≥65%）时，在改动任何东西之前，先应用这条**三步决策规则**：

**Step 1 —— 词性检查。** 被抹掉的词是不是虚词（the / a / an / of / in / on / at / to / I / it / is / are / was / be / that / this / which / and / or / but）？虚词在大多数语境下语法上是可有可无的 —— 一个被 100% 吃掉的 "the"、"I" 或 "of" 通常**不会**让句子坏掉。实词（名词、动词、形容词、高潮词）承载意思 —— 它们**必须**保持可读。

**Step 2 —— 去掉这个词后解析句子。** 在脑子里把被抹掉的词从句子里删掉。剩下的部分还能传达意思吗？

- "like this are why I travel" 去掉 "I" → "like this are why travel" —— 从上下文看第一人称很明显，**OK**
- "take it all in" 去掉 "all" → "take it in" —— 本身就是一个完整的英语习语，**OK**
- "a whole lot of information" 去掉 "of" → "a whole lot information" —— 有点破，但能还原，**OK**
- "diving deep into startups" 去掉 "deep" → "diving into startups" —— 完全没问题，**OK**
- "diving deep into startups" 去掉 "diving" → "deep into startups" —— 丢了动词，句子坏了，**NOT OK**

**Step 3 —— 电影感检查。** 单个实词被部分遮挡 30–65%，正是*预期的*嵌入效果（Vogue 刊头式的"主体擦过文字"）。不要去"修"它。只有在以下情况才升级为重新布局：

- 某个实词 ≥80% 消失（不只是被部分吃掉 —— 几乎完全缺失）
- 两个或更多相邻的词 ≥50% 被抹掉（连续的损伤会叠加；"X X X really takes" 前三个词被吃掉就无法还原）
- 被抹掉的词**就是**高潮 / 观众应该读到的关键名词（例如句子的主语、品牌名、产品功能）
- 高潮词的关键字母被吃掉（例如 "STARTUP" 丢了 S 就读成 "TARTUP" —— 残缺字母的形态比整词百分比更重要）

**来自 13 个案例批次的真实例子** —— 下面四条字幕都拿到了逐词抹除的 FAIL，四条都被这条规则正确地判定为 OK：

| 案例               | 被抹掉的词 @%       | 句子                              | 应用的规则                           |
| ------------------ | ------------------- | ------------------------------------- | -------------------------------------- |
| Sunset_Stroll cg-1 | "I" 100%            | "like this are why I travel"          | 虚词 + 去掉后能解析 → OK |
| Sunset_Stroll cg-3 | "all" 75%           | "take it all in"                      | "take it in" 是完整的习语 → OK  |
| yt_gtds cg-6       | "of" 69%            | "a whole lot of information"          | 虚词 + 能还原 → OK       |
| AI_Insights cg-2   | "that" 66%          | "that don't replace human creativity" | 关系代词，可有可无 → OK        |

**当规则判定需要重新布局时** —— 改什么：

- 逐词被抹掉，**并且**是实词，**并且**破坏了可读性 → 把那一条字幕单独切到 `layer: "fg"`（按字幕覆盖，不是整个 plan），**或者**缩小 / 重新定位，**或者**把这条字幕拆到另一个主体不横穿它的块里。
- 整个堆叠都在头部区域时的逐字幕失败（峰值 ≥50%）→ 抬高 y 或缩小这个块。
- 画面边缘溢出 → 缩小字号，**或者**收紧 `letter-spacing`，**或者**拆分短语。被裁切的文字**永远**是错的，没有审美上的借口。

**覆盖**（用于交付前的迭代）：`OCCLUSION_SKIP=1 bash render-and-composite.sh <project>` —— 在没有应用三步规则、并逐个修复或有意识地接受每个 FAIL 之前，不要越过它交付。

### 累积容量 —— plane 装不下时拆成块

每个场景的干净区域，对能同时被读清的字幕数量是有限容量的。**agent 必须在写 plan 之前判断这一点**，而不是依赖 CSS 的 `bounded height` / `overflow: hidden` —— 那些会造成视觉 bug（字幕溢出画面、被裁切，或者内容在 plane 边界之外被居中）。

经验法则（容量 = 一个块内**同时**可见的最大字幕数）：

- **9:16 竖屏，窄的右侧栏 plane**（宽约 380–420px）→ 每块最多 **2 条字幕**。长短语会折成 2–3 行；第 3 条字幕就开始溢进主体了。
- **16:9 横屏，主体居中**（例如自拍 vlog）→ 每块最多 **2 条字幕**。即使画面更宽，居中的主体也只在两侧留下窄栏，而且手能伸得很远。
- **16:9 横屏，主体在一侧**（例如另一侧干净的访谈 —— memory-wall 标准范例的场景）→ 每块最多 **3–4 条字幕**。这正是累积大放异彩的地方。
- **顶部全宽横带 plane**（任一朝向）→ 最多 1–2 条字幕，再多就溢进脸部区域。

容量取决于具体场景 —— 同样的朝向，因主体位置和背景复杂度不同，可用空间可能相差很大。

当你的短语数超出容量时，在**句子或分句边界**处拆成多个累积块。以 memory-wall 标准范例的 12 词片段为例：

- Block 1（0–4.85 秒）：`"Some memories feel soft"` + `"like old film"` —— 2 条字幕累积，在 4.85 秒一起淡出
- Block 2（4.90–8.04 秒）：`"but suddenly"` + `"EVERYTHING IS SHARP AGAIN"` —— 2 条字幕在清空后的 plane 上累积

同一个块里的所有字幕共享同一个 `out` 时间（句子边界）。下一个块的 `in` > 上一个块的 `out`，这样新一轮累积开始之前 plane 就清空了。这给每条字幕约 3–5 秒的阅读时间，避免拥挤，并且契合 memory-wall 的电影节奏。

**为什么共享 `out` 至关重要。** 模板的退场路径是 `tl.set(sel, { opacity: 0, display: "none" }, g.out)` —— 在 `out` 时刻，每条字幕释放它的 flex 空间，让**下一个**块的字幕能从 plane 的原点占据最上面的位置（不会永久地往下漂移）。如果同一块内的字幕 `out` 时间是错开的，plane 就会在块中途重排（字幕 1 消失，字幕 2–3 往上跳，字幕 4 到来…… 可见的抖动）。有了按块同步的 `out`，重排只在边界处发生**一次** —— 观众看不出来，因为整个块作为一个单元淡出。**绝不在一个累积块内错开 `out` 时间。** 如果你需要逐条淡出，那你就不是在累积 —— 切换到错开淡出模式（一次一个分组，不需要 flex plane）。

**反模式：在 plane 上用有界 `height` + `justify-content: center`。** **不要**在 flex 列 plane 上写 `height: 70%; justify-content: center`，指望以此把字幕垂直居中。当块里字幕的总高度超出有界高度时，flex 居中会把内容同时往上**和**往下推出 plane 边界 —— 最顶上的字幕最终跑到画面之上（出画、读不到）。正确做法：

- 让 plane 随内容增长 —— 设 `top:`（原点锚点），让字幕自然地向下堆叠。
- 字幕之间用 `gap:`；不要试图"把堆叠居中"。
- 相信上面的块容量规则能把堆叠控制在干净区域内 —— 不要用 `overflow: hidden` 掩盖溢出（它裁掉的正是你想让观众读到的字幕）。

### 累积 —— 垂直间距，而不是单行

累积对多行短语同样适用 —— memory-wall 标准范例的分组都是多词的，在 16:9 横屏中右对齐瀑布式排列，其中好几个折成了 2 行。它们之所以不相撞，是因为**每个分组的 `top` 都放在上一个分组底部范围之下，并留有边距**。

交付累积之前你必须算的数：

对每个分组，估算它渲染后的高度：

- `line_count ≈ ceil(chars × font_px × 0.72 / usable_width_px)`（0.72 = Inter 900 全大写；斜体 / 常规体用 0.60）
- `group_height_pct ≈ line_count × font_size_pct × line_height × 100`

然后对你想让它们共存的每一对（cg-N, cg-N+1）：

- `cg-(N+1).top ≥ cg-N.top + cg-N_height_pct + 2%`（边距）

如果算出来在可用的干净区域里放不下（顶部干净区 + 底部干净区，减去脸 / 身体的包围框），你有两个选择：

- **缩小字号或合并短语**，让它们放得下。
- **把持续方式切换为错开淡出**（分组不共存，没有间距约束）。

具体到 9:16 竖屏：干净区域通常是顶部 0–32% + 底部 72–90%，被主体分隔开。可用的大约是画面高度的 50%。按每个 2 行分组 15% + 2% 边距算，顶部区域大约能放下 3 个累积分组。第 4 个必须要么 (a) 更小以便放下，要么 (b) 去底部区域（在句子边界处允许切换区域），要么 (c) 作为高潮取代之前的某一个。

16:9 横屏有约 70–80% 的可用垂直空间 —— 能容纳 4–5 个累积分组，这就是 memory-wall 标准范例在那里干净利落的原因。不要在竖屏上放弃累积；只是要先把算术做了。

### 持续时长 —— 每个分组停留多久（agent 按案例决定）

分组的 `out` 时间不是默认值，不是规则，也不是公式。它是一个审美选择。同一个 5 分组的 plan，取决于分组是累积、错开、交叉淡化还是滚动，渲染出来会非常不同 —— 而每一种都适合不同的内容。

可以挑选的模式：

| 模式                                     | 会发生什么                                                                 | 适合                                                                                            | 不适合                                                            |
| ------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **累积直到高潮**（memory-wall） | 所有分组都留在屏幕上直到高潮到来，然后一起淡出       | 诗意的铺陈；情绪的渐强；≤5 个分组且每个词都重要                               | 8 个以上分组（屏幕拥挤）；有冲击力的喜剧段落节拍（打断笑点） |
| **错开淡出**（Sunset 风格）             | 每个分组在其词说完后约 0.8–1.5 秒淡出；下一个进入干净的空间 | 相互独立、有冲击力的段落节拍；每个短语都是独立时刻的片段                                  | 希望各个诗节共存的长篇诗意铺陈                |
| **交叉淡化交接**                       | 当前分组在下一个入场期间淡出（约 200ms 重叠）                  | 密集的逐字内容（短片段里 6 个以上分组）；对话式的流动                                       | 短而稀疏的片段 —— 感觉像字幕轨                     |
| **滚动窗口**                          | 保持 N=2–3 个可见；N+1 入场时最早的那个淡出                           | 较长的转写稿（15 秒以上），完全累积会拥挤，但一定的分层仍有电影感 | 短于 8 秒的片段（感知不到滚动）                              |

决策维度：

- **叙事弧线** —— 渐强 / 揭晓 → 累积；一串相互独立的要点 → 错开；密集的对话 → 交叉淡化
- **分组数** —— ≤4：任何模式都行。5–7：优先错开或滚动。8 个以上：通常只能交叉淡化。
- **场景密度** —— 繁杂的背景会吃掉停留过久的字幕；只有背景足够干净、较早的字幕仍然可读时，累积才行得通。
- **片段长度** —— ≥12 秒会削弱累积效果（观众失去与最早那条字幕的联系）；长片段优先错开或滚动。

把推理写进 plan.json 的 `_notes`，让决策可以被检查，agent 的意图也能保留到评审阶段。例如：

```json
"_notes": "Morning_Jog: 5 groups in 8s. Narrative is crescendo (Okay→honestly→changed my life→KIDDING), and background is clean (trees, sky). Accumulate-through-climax — all 4 earlier groups stay visible so KIDDING lands on top of a built-up poem. Cascading right with varied top%/alignment so the stack reads as composition, not a subtitle column."
```

这正是按案例判断体现价值的地方。skill 给你一个模式色板；挑哪个由你决定。

### 空间一致性 —— 主位规则

**每个 plan 都有一个主位。** 大多数分组落在那里。次位只为刻意的节奏打破而存在（约每 30 秒一次，绝不逐个碎块交替）。旧的自动生成轮换把每个碎块扔到不同的角落，违反了这一点，读起来一片混乱。

根据场景选择主位：

- **9:16 竖屏，主体在画面中部** → 主位是 `top: 4–20%`（天空 / 头顶上方的干净区域）。次位：`top: 72–78%`（肩膀下方、UI 上方）。绝不：底部 22%（按 [rule 17](aesthetic-principles.md)，那是 UI / 手的区域）。
- **16:9 横屏，主体在左** → 主位是右侧栏（`left: 50–55%`，在栏内右对齐或居中）。次位：主体下方。
- **16:9 横屏，主体居中** → 主位是 `top: 10–20%` **或** `top: 70–80%`。挑一个并坚持下去。

在主位之内，通过变化**字号和字重**来建立层级（narrator 小、正文中、强调大、高潮巨大）。这就是一个一致位置内部的节奏。次位是给**打破节奏的时刻**用的，不是给相邻碎块用来"避免碰撞"的。

碰撞校验器依然会运行 —— 但现在 agent 应该只在例外情况下（刻意分层）才触发它，而不是因为每个碎块都在不同的位置。

**逐字配方** —— 每个词都显示，但它**不是**一条平铺的 TikTok 字幕 rail。要用电影感的 DNA：按分组变化字体排印、变化位置、调节字号。斜体开场、正体支点、全大写高潮、空间瀑布式排列、逐词 soft/present 语气 —— 全都要。

切块：遍历转写稿，在停顿边界处拆成 **1–4 个词**的分组（>0.25 秒的间隔 = 硬切；在一个短语内部，按情绪节拍切块 —— 强调词用 1–2 个词的短块，起连接作用的部分用 3–4 个词的长块）。

每个碎块的字体排印 —— 把每个碎块当作一个迷你段落节拍。下面的字号是**起始色板，不是规则。** agent 根据场景干净区域的宽度、短语的字符数，以及相对相邻分组想要的视觉分量，为每个分组挑选实际的 `font-size`。只要场景需要，就上下浮动 ±30%（窄的竖屏栏 → 缩小；宽的横屏 hero → 放大）。从 [typographic-moves.md](typographic-moves.md) 里挑：

- **填充 / 连接**（"you know"、"like"、"so I was"、代词、连词）→ 斜体 500–600，小（起始约 0.05–0.08h），更柔和的语气，从属位置。这些读起来是 narrator 的声音，而不是陈述。
- **强调 / 实词**（承载意思的动词、名词）→ 正体 600–800，中（起始约 0.08–0.12h），居中或瀑布式位置，present 语气。
- **高潮 / 钩子词**（句子的落点词）→ 全大写 800–900，大（起始约 0.14–0.22h），全画面或接近画面宽度，present 语气加缩放弹出。

**字号永远是相对的，绝不是绝对的。** 重要的是同一 plane 内一个分组与相邻分组之间的*对比比例* —— 高潮应约为强调的 2 倍，强调约为 narrator 的 1.3–1.5 倍。一个给 plane 里三条字幕写出 `0.08h / 0.08h / 0.08h` 的 agent，不管它是从哪一档挑的，都已经失败了。层级才是重点。

空间构图：把整个画面当画布用。填充类碎块缩在角落或以小字号待在从属位置；强调类碎块占据中间；高潮类碎块拥有整个画面。**不要把所有东西都锁在 `bottom: 12%`** —— 那就是无聊字幕的陷阱。

时间窗口：要么让重叠的分组在空间上分开（瀑布式排列、诗式累积），要么做交接，让一次只显示一个碎块。在同一个位置交接读起来很抖（短时间窗口里切换太多）—— 优先用空间瀑布式排列，让相邻碎块在不同位置共存，或者用以句子为边界的累积块。

图层：只要碎块所在位置周围有干净的场景（天空、墙面、主体上方 / 下方的区域），就默认用 `"bg"` —— 那就是嵌入效果。只有当碎块所在位置会被身体遮挡 ≥80% 时才用 `"fg"`（例如 9:16 竖屏中放在底部、躯干占满那片区域的新闻条式碎块）。

**横穿主体的高潮碎块 —— 可读性第一。** Vogue 刊头效果（巨大的全大写横穿身体）是最有电影感的手法，但前提是这个词仍然可读。只有当以下条件**全部**满足时，才在主体上方使用 `bg`：

1. 字幕是多行的（≥2 行），这样即使某一行大部分被吃掉，其他行仍然干净，观众能读出这个短语。单行字幕绝不应直接压在脸 / 身体上 —— 要么重新定位到主体上方 / 下方，要么用 `fg`。
2. 主体的包围框覆盖不超过字幕总像素面积的 40%。对于 9:16 竖屏中典型的头肩主体（在画面中部约占 30% 垂直 × 约 50% 水平），一条位于 `top: 16%`、4 行 × 0.14h 的字幕满足这一点 —— 脸吃掉一行，另外三行读起来很干净。一条位于 `top: 40%`、直接压在脸上的字幕则不满足。
3. 每个单独的词至少在一侧有可见的字母端点 —— 一个在字母中间被劈开、只露出内部笔画的词是读不了的，即使只有"总像素的 25%"被覆盖。

只要其中任何一条不满足，要么把 BG 字幕**重新定位**到干净的场景（头顶上方 / 肩膀下方 / 偏离中心的角落），要么**退回到 `fg`**。当场景没有足够大的干净区域时，高潮用 FG 是正确的选择 —— 不要以牺牲可读性为代价硬上嵌入美学。

经验法则：如果把你的 plan 压扁到只剩高潮碎块，结果应该仍然读起来像一条令人满意的推文长度标题。如果不是 —— 说明你的字体排印变化不够，高潮跳得不够狠。
