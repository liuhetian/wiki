先读[调研项目的共用证据规则](index.md#evidence)，再读实现材料，README 当线索。源码、prompt、配置和引用文件按项目实际形态查看。有概要或已确认的关注点就沿用，不重复询问；未给关注点则覆盖主要功能，不为粗讲强制盘问 baseline 或功能线。

## 按功能讲清

- 默认一篇，正文参考 3000–6000 字；篇幅服从内容，不凑字数，不强套论文骨架。活例：[wenai](../../projects/wenai/index.md)。
- 开头交代它是什么、解决谁的问题、主路径和分工；每个主要功能一个板块，相关的小功能可合并。
- 每个板块讲清“具体问题 → 怎么做 → 材料长什么样 → 效果和边界”。有关注点的部分讲深，其余交代到看得懂主路径。
- 读者应看得到机制的具体载体：源码片段、prompt、配置、数据结构、状态文件、输入输出或界面，按项目选，不要求样样齐全；有跨轮状态就展示前后文件和下一轮实际拿到的内容。
- 材料要能对应原项目；过滤、改写、补造的示例按共用证据规则标明。不要只列功能名或抽象形容，也不要补出上游没有的工程实现。
- 末尾说明程序、模型、宿主与使用者各管什么，以及主要局限；不追成细讲式的逐步设计推导。

## 实跑怎么取舍

按需时，静态材料足够说明的直接讲；关键效果仅凭阅读无法确认、或对照能明显帮助理解时，拆出最小片段实跑，不要求部署整个项目。选“是”时实跑所讲的关键机制；跑不了的说明原因和未验证范围。选“否”时不执行项目或调用模型，只展示材料和明确标出的示例。

有可执行核心时优先跑原项目实现；没有代码的 skill 或配置仓库，可以做明确标为构造的机制演示，不能用它声称原项目已经验证。脚本、输入输出和实验设置进维护，正文放读者理解所需的效果，具体证据要求见共用规则。

有前端且需要解释界面时，照[展示别人的界面](../wiki-guide/reference/components.md#showcase-demo)做源码支持的仿真 demo；配图仅在用户明确要求时做。
