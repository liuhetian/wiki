# 从已有项目整理文档

给一个已经在跑的项目补文档时走这六步，写成[使用 wiki 管理项目开发](index.md#docs)定的那几个板块。从零开发的项目边做边写，不用走。

一共六步，**问人分两轮**。第一轮问背景，要早问，因为背景决定了深入探索时把重点放在哪。第二轮问的是只有读完代码和线上数据才提得出来的问题，比如确认推断、解释反常的地方。只问一轮的话，要么问题很空，要么文档里留下一堆「推断」。

## 第一步：浅探索（几分钟）

只建立整体印象，不深读：

- README、CLAUDE.md、已有文档、目录结构；
- git log：提交数、时间跨度、作者、远程仓库；
- 依赖和语言；
- 它是怎么跑起来的：systemd、docker、cron、xxl、airflow，还是靠手动启动。

结束时要能用三句话说清这个项目是什么。

## 第二步：第一轮提问（开放问题）

先把那三句话给用户看，让他纠正。然后问：

- **这个项目平时叫什么名字？**（必问）它会用作 `index.md` 的标题和主 wiki 导航里的名字。仓库名、目录名、服务名常常各不相同，也未必是大家口头的叫法，**不要自己起名**。

再从下面挑问题来问：

- 这个项目当初为什么做？要解决什么问题？是谁提的需求？
- 有哪些是你知道、但代码里看不出来的？比如谁在依赖它、有哪些口头约定、有哪些已知问题。
- 有没有不能碰的东西？比如生产库、不能重启的服务、不能连的环境。

问题一次性列出来，不要一个一个地追问。

**不要问规范里已经定死的事**：文档给谁看（所有读者都要照顾到）、放在哪里（`docs/`）。

## 第三步：深探索（代码 + 运行现状）

**代码**：入口和数据流、后台任务和定时逻辑、配置与环境变量、外部依赖（包括不在依赖清单里的，比如 `sys.path.append` 引进来的库）、测试怎么跑。

**运行现状**（最容易漏，必须单独看）：进程状态与最近的日志、数据库里的量和分布（只看聚合，不导出原始行）、定时任务配置、实际上是谁在调用它。用户、用量、哪个配置真的在用、失败率，这些往往在线上数据里，而不在代码里。

**只读原则**：查 SQLite 用 `sqlite3 -readonly`；不重启服务；不在同一个目录或同一个库上再起一个实例；不带生产凭据跑测试；不触发通知。

**专门找新人会踩的坑**，逐项检查：

- [ ] 重启或停机有什么副作用（比如正在跑的任务被标成失败、积压的任务被一次性放出去）
- [ ] 共享状态：多个实例共用一个库？默认配置会不会连到生产？
- [ ] 看起来像废弃、其实在用的东西：名字里带 test、副本、old、bak 的，先查使用量再下结论
- [ ] 以谁的身份在跑、有什么权限；这个账号停用会怎样
- [ ] 隐式依赖：别的目录、别人的环境、写死的路径或 IP
- [ ] 密钥和凭据放在哪；有没有进 git、有没有推到远端
- [ ] 没有备份的数据
- [ ] 时区假设
- [ ] 线上实际部署的文件（unit、配置）和仓库里那份是否一致

同时**收集时间线的候选节点**：

- git：要读 diff 来归纳，不能只看提交信息，提交信息常常只有一个 "fix"；
- 线上数据：每个功能第一次被真实使用是哪天；
- 代码注释和提交信息里出现的日期与事故。

## 第四步：第二轮提问（针对性问题）

只问上一步发现、而且只有用户知道答案的问题：

- 确认推断：「X 看起来是 Y 在调用，对吗？」
- 解释反常：「这个模板名字叫副本，但每天都在跑，要改名吗？」
- 挑里程碑：把时间线候选列出来，让用户勾选，并补上「为什么」。
- 发现的问题（bug、反常、安全隐患、缺备份……）：每条让用户选「记入 TODO」或「不管」。

能给选项就给选项。最多 5 个问题。用户答不上来的，有依据就写成「（推断）」，没依据就留占位符。

## 第五步：写

- 每条事实都要有来源：代码、数据、用户说的，或推断。推断的标「（推断）」并写明依据；用户说的不用标。
- 不知道的不要编。留占位符 `<这里可以补充：……>`，把要补什么写具体，例如 `<这里可以补充：2025-07 为什么关闭命令白名单>`。
- 用户说「不管」的问题，哪个文件都不写。
- 数字带口径和截至日期，例如「近 30 天 768 个任务，截至 10-13」。
- **密钥只写位置，不写值**。token、bot id、密码、内网连接串都一样。
- 指向代码用 `文件:行号`。
- 写「为什么」，不只写「是什么」。
- 先结论后细节。对照类的内容用表格，操作类的内容用步骤或命令。
- 不夸大，不凑字数。没有就省略，不写「暂无」。
- 同一件事只写在一个文件里，其他文件用链接引用。

## 第六步：交给人审

交付时用几行话说明：

- 写了哪些文件；
- 要进主 wiki 的，提醒用户在主 wiki 的仓库里让 agent 照[吸纳子 wiki](absorb.md)收一遍；
- 哪些内容是推断的；留了几个占位符、分别在哪，好让用户知道去哪里补；
- 哪些没查到（权限不够、拿不到数据）；
- 第二轮里用户选了「记入 TODO」的问题，是否都已写进 `todo.md`。

**不要擅自提交 git。**
