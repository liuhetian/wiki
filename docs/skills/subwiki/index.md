# 使用 wiki 管理项目开发

自己开发的项目，文档写在自己仓库的 `docs/` 里，和代码一起维护，再由项目的服务把它挂成一个 wiki 站点：人读 HTML，AI 读 `.md`。两件事都要做：先守[共同约定](#contract)，照[给项目写文档](#docs)写，再照 [wiki 部署约定](#site)挂出来。活例：[牛牛便利贴](../../projects/clipboard/index.md)。如果要调用 2 次以上本 skill 中的脚本，直接将[本 skill](subwiki.tar.gz)下载到本地。

用到才读的：

- [本 wiki 写作规范](../wiki-guide/index.md) —— 动笔写正文时读：[文风](../wiki-guide/index.md#style)、[每页一行 description](../wiki-guide/index.md#description)、[什么场景用什么语法](../wiki-guide/index.md#syntax)里的标准语法；写作流程、放哪个板块、nav、check-links 和自研组件管的是主 wiki 自己，不适用
- [从已有项目整理文档](from-existing.md) —— 给一个已经在跑的项目补文档时读；从零开发的照本页的板块边做边写，不用读
- [动态数据](live.md) —— 要在文档里嵌接口的实时数据时读
- [吸纳子 wiki](absorb.md) —— 要把项目的 wiki 收进本 wiki 的项目板块时读，在本 wiki 的仓库里做；收进来的这份叫子 wiki，本 wiki 是主 wiki

## 共同约定 { #contract }

写文档和建站都要守；要收进本 wiki 的，吸纳时逐条核对，不符合的退回项目改：

- **源文件在项目根的 `docs/`**，入口是 `docs/index.md`，frontmatter 写一行 `description`
- **每一页都能从某个祖先目录的 `index.md` 顺链接走到**：AI 只顺链接读，没挂上的页面对它不存在
- **页面之间的链接写相对的 `.md` 路径**（`../concepts/numbers.md`）：写成目录形式，AI 读到的是 HTML
- **链接不指向 `docs/` 之外**：整个目录会被拷走，指到外面的链接全部失效
- **有页面链回 `index.md` 的，`index.md` 的 frontmatter 写 `copy_source: true`**
- **只用 Material 的标准语法**：折叠、选项卡、提示框、代码注解、表格、脚注；mermaid 可以用。主 wiki 的[自研组件](../wiki-guide/reference/components.md)在项目自己的站点上不生效
- **`reference`、`assets`、`scripts` 不当 `.md` 文件名**：和同级目录撞网址
- **文字照[本 wiki 写作规范](../wiki-guide/index.md)里适用的三节**：文风、description、标准语法

## 给项目写文档 { #docs }

文档要人来维护，每个字的位置都珍贵。从零开发的项目照下面的板块边做边写；给已经在跑的项目补文档，另照[从已有项目整理文档](from-existing.md)的六步走。

### 板块

固定放在项目根目录的 `docs/`，分成下面这些板块，名字在所有项目里都一样：到任何项目，运维问题都看 `ops`、历史都看 `timeline`。一个板块可以是一个 `.md`，也可以是一个同名目录 —— 内容多了就拆，比如需求按模块拆成 `requirements/index.md` 加各模块一页。名字用英文、标题用中文，避开 git 和 URL 里的中文转义。接口参考、上手指南这类其他内容各开子目录。

```text
docs/
  index.md      入口：一句话 + 背景 + 现状（截至 YYYY-MM-DD）+ 文档目录
  requirements  需求：功能和规则应该是什么样，项目以它为准
  ops           部署与日常维护
  dev           架构、代码地图、测试、坑
  timeline      时间线：功能 / 上线 / 事故 / 决策
  todo          要处理的问题，一句话一条
```

各板块按**多久会过期**来分工。这条分界一定要守住，因为数字过期了，运维步骤往往还是对的：

| 板块 | 寿命 | 怎么维护 |
|---|---|---|
| `requirements` | 长期有效，人维护 | 人只维护这一个：改功能先改它，代码和其他板块跟着它走；和代码对不上时以它为准 |
| `index.md` | 快照 | 现状一节的标题写「截至 YYYY-MM-DD」，每次更新整节重写 |
| `ops` `dev` | 长期有效 | 跟着代码一起改，只改已经不成立的地方 |
| `timeline` | 只追加 | 旧条目不改，新条目加在后面 |
| `todo` | 长期有效 | 做完就删掉，不打勾留着 |

#### 各板块写什么

**`index.md`**（必有，控制在一屏以内）

```markdown
# <项目名：用户平时的叫法>

一句话：它是什么、给谁用。仓库名、目录名、服务名写在这里，方便搜索。README 已有的功能和接口说明不重复，放一个链接。

## 背景
为什么做、要解决什么、谁在用。主要来自用户的回答。不带日期，不讲哪天做了什么、怎么一步步变成现在这样 —— 那是时间线的事。

## 现状（截至 YYYY-MM-DD）
线上实际跑成什么样：谁在用、用量与成功率、关键配置的实际使用情况，几行写完。数字带口径。不写功能和规则，那是需求的事；还没上线的不写这一节。

## 文档目录
| 文件 | 讲什么 | 什么时候读 |
|---|---|---|
| requirements.md | …… | 要改功能、要判断某个行为对不对时 |
| ops.md    | …… | 服务出问题、要重启、收到告警时 |
| dev.md    | …… | 要改代码之前 |
| timeline.md | …… | 想知道某段代码或规则为什么是这样时 |
| todo.md   | …… | 想知道有哪些已知问题要处理时 |
```

「什么时候读」这一列给 AI 判断该打开哪个文件，要写成具体的场景。

**`requirements`**：功能和规则应该是什么样，用户靠它管整个项目。开发期间要有一份一个人能掌控住的文档，一句话一个需求，一份装不下就按模块拆成几份。写到能照着验收；其他文件讲到功能和规则时链过来，不转述。用户已经有需求文档的，整份挪进来，正文不改。

**`todo`**：**只收用户确认要处理的问题**，一句话一条，写清是什么问题、在哪里（`文件:行号`）、什么时候发现的：

```markdown
- 任务成功后仍往默认群发通知：队列表的 notify 默认值覆盖了模板配置（worker.py:212，2025-09-01 发现）
```

用户说「不管」的问题，不写进 `todo.md`，**也不写进其他任何文件**：它可能就是个小问题，不值得占文档的位置。

**`ops`**：部署在哪（机器、路径、进程管理、端口、数据文件、外部依赖）、常用命令、告警含义和处理办法、重启或停机的副作用、怎么只读地查数据。

**`dev`**：架构（入口 → 处理 → 出口、后台任务、容易忽略的行为）、代码地图（用 `文件:行号` 表示）、怎么跑测试、改代码会踩的坑。

**`timeline`**：写法见下文「时间线怎么写」。

#### 什么时候不建、什么时候拆

- **没内容就不建。** 某个板块写不出实质内容时就不建，在 `index.md` 的目录里注明「无」，不要为了凑结构写空话。小项目可能只有 `index.md` + `ops.md` + `timeline.md`。
- **太长就拆成目录。** 某个板块超过约 300 行，或者里面有一块能独立成篇的子系统时，就把它拆成同名子目录，子目录里放一个 `index.md`，写法同上。例如 `dev.md` 拆成 `dev/index.md`、`dev/scheduler.md`、`dev/bridge.md`。
- **最多两级。** 不要提前建好空的子目录。

#### 让以后的 agent 记得 { #remember }

以后在这个项目里干活的 agent 不会读到本页，所以把下面几行写进项目的 `CLAUDE.md` 或 `AGENTS.md`：有哪个写哪个，都没有就新建项目在用的 agent 认的那个。只写这几行，不把文档内容塞进去 —— 这两个文件每次会话都整份加载。

```markdown
## 文档

- 项目文档在 `docs/`，入口 `docs/index.md`。功能和规则以需求为准，改功能先改它
- 文档照 <本页的网址> 的约定写，动 `docs/` 之前先读
- 改了 `docs/` 要重新构建并部署 wiki：`<构建和部署的命令>`；部署项目时 wiki 一起上线
- 增删了页面，提醒我让主 wiki 重新吸纳一遍
```

最后一行只在这份 wiki 被主 wiki 收了的项目里写。

### 时间线怎么写 { #timeline }

只收会改变读者理解的节点，不写成 changelog。一张表四列：日期、类型（功能、上线、事故、决策）、内容、为什么或影响。

| 日期 | 类型 | 内容 | 为什么 / 影响 |
|---|---|---|---|
| 2025-08-11 | 事故 | 连接静默断开，服务停摆 20 小时没有告警 | 所以加了看门狗和语句超时，见 `worker.py:310` |

## wiki 部署约定 { #site }

项目的服务进程自己把 wiki 挂出来：只监听一个端口，不依赖 nginx。wiki 只占 `/wiki/` 一个前缀，其他路径都归服务自己。

| 路径 | 内容 |
|---|---|
| `/wiki/x/` | 给人看的页面，构建产物 `site/x/index.html` |
| `/wiki/x.md` | 给 AI 读的源文件，`site/x.md` |

### 配置

`zensical.toml` 放项目根：

- **`site_url` 写服务对外的地址加 `/wiki/`**，路径和服务里挂载的前缀一致。地址只写在这一处
- **`use_directory_urls = true`**：页面占 `x/index.html`，`x.md` 这个位置才空得出来
- **`nav` 写全**：主 wiki 吸纳时照它排顺序
- **用到的语法要开对应的扩展**：折叠要 `pymdownx.details`，选项卡要 `pymdownx.tabbed`，提示框要 `admonition`；没开的照样构建通过，只是渲染成一段普通文字
- **不开 macros 插件和 smarty 扩展**：用到[动态数据](live.md)时，前者在构建时把 `{{ }}` 吃掉，后者把直引号换成弯引号

### 构建

项目自己构建自己的站点；主 wiki 不参与，它只拷 `docs/` 里的源文件。两步：

1. `zensical build` 生成 `site/`。这一步会清空 `site/`，下一步必须在它之后
2. 把 `docs/` 下的 `.md` 按原目录结构复制进 `site/`：

    ```bash
    rsync -a --exclude='.*/' --include='*/' --include='*.md' --exclude='*' --prune-empty-dirs docs/ site/
    ```

想让页面的 `<head>` 带上指向 `.md` 的 `<link rel="alternate">`、顺带查失效的相对链接，有现成的[后处理脚本](scripts/postbuild.py)（要连同 [`placeholders.py`](scripts/placeholders.py) 一起拿）和把三步串起来的[构建脚本](scripts/deploy.sh)，放哪由项目定。

### 挂载要守的

- **每次请求现读 `site/`**：构建完立即生效，不用重启
- **`.md` 返回 `text/markdown; charset=utf-8`，同时支持 HEAD**：有的抓取器先发 HEAD 看类型，类型不是文本就不读
- **`/wiki/x` 是目录时跳转到 `/wiki/x/`**：不跳的话页面里的相对链接全部解析错
- **路径解析后必须还在 `site/` 里**，否则 `../` 能读到项目的其他文件
- **`/wiki/` 之外找不到的路径返回服务自己的 404**，不返回 wiki 的 404 页面

服务跑在 EdgeOne Makers 这类边缘平台上的，没有「服务进程」：页面是平台直接给的静态文件，只有 `.md` 落到函数。先读[边缘函数的限制](../edgeone/reference/functions.md)：`.md` 原文要打进函数包；函数按文件夹分配请求，接口和 `.md` 共用最顶层的一个入口，别给 wiki 另开一个。
