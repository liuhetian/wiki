# 约束卡（guard） · 3 张

不产出内容，只给模型加一道闸：没满足条件前不许往下走。原文照录自 [prompt-cards.cyanfish.site](https://prompt-cards.cyanfish.site/)，prompt 正文一字未改，标题、稀有度和一句话摘要都是站点自带的字段；抓取方式与版本见 [MIRROR](../MIRROR.md)，怎么挑卡见 [入口页](../index.md)。

## 约束·范围铁闸 { #trap-scope }

`R` —— 强制模型先划边界，防止范围蔓延与过度设计。

```text
在给出任何实现建议之前，你必须先完成「范围锁定」：

1. 用一句话定义「完成」长什么样
2. 列出最多 3 条必须做的事
3. 列出至少 3 条明确不做的事
4. 指出最大风险点（一个）

若我的需求过大，先提议可交付的最小切片，再问我是否继续。
未完成以上步骤前，禁止写代码或长篇方案。
```

## 约束·人话翻译 { #trap-plain }

`N` —— 禁止行话堆砌，强制用大白话把复杂概念讲清楚。

```text
用中学生能听懂的话解释下面的概念。规则：

- 禁止堆砌英文缩写；若必须出现，立刻用括号解释
- 先用一个生活类比，再用技术对应
- 全文不超过 200 字
- 最后用一句话说明「什么时候你会用到它」

概念：
{{concept}}
```

## 约束·实事求是 { #trap-facts }

`UR` —— 现状须核实；文档只作线索，过时则交叉验证后再下结论。

```text
对涉及「本机现状、现场配置、已安装工具、路径、版本、命令、项目文档」的问题，你必须遵守「实事求是」：

1. 作答前先用可用手段核实（读文件、跑命令、查本机状态、对照代码与文档）；未核实前，不得写成确定结论或可照抄的命令
2. 禁止用「官方常用写法 / 行业惯例 / 我猜的 / 一般大家都这样」替代本机或仓库内的证据
3. 文档（README、spec、ADR、注释、外部文档）仅作线索，不默认等于现状：可能过时或与实现脱节；引用文档结论前，须用代码、配置或可执行检查交叉验证；冲突时以已核实的现状为准，并标明文档与现实的差异
4. 给出安装、升级、路径、版本、配置类建议时：命令与步骤必须匹配实际安装方式与当前环境；不确定就先查或先问，禁止默认套用某一包管理器或某套路径
5. 证据不足时：明确写「尚未核实」，并列出还缺的具体事实（一条一条列清）；禁止用听起来很对的默认答案填坑
6. 若发现先前建议与已核实事实冲突：立刻纠正，并说明依据是什么

非「本机/现场/文档可信度」类问题可正常推理；一旦落到可核验的现状，以上规则优先于流畅与自信。
```
