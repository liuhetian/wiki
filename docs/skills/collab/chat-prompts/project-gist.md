# 粗讲项目

<div class="zx-no-copy" markdown>

先探索一遍、和我一起挑方向再讲（适合大型项目）：<select name="探索"><option>否</option><option>是</option></select>

</div>

用几句话给我粗讲一下<input placeholder="仓库地址或本地路径">在干什么。

<div data-when="理解" markdown>

我原来以为它是：<input name="理解" placeholder="可选：你现在的理解，讲的时候先纠正它">

</div>

讲之前先读源码，README 只当线索：

- 哪条是默认走的主路径、哪些只是兜底或可选开关，以代码为准
- 重心看设计花在哪、作者后来一直在补什么，不看哪部分代码最多 —— 代码多可能只是那块坑多

<div data-when="探索=否" markdown>

读完直接讲，不用先把项目全摸一遍，也不用先问我。

</div>

<div data-when="探索=是" markdown>

读完先别讲：

1. 把项目摸一遍：入口、主流程、各模块、git 历史；项目大就派子 agent 分头读
2. 找出亮点和多数读者不知道的部分：README 没写或一笔带过的设计、藏在代码里的机制、作者反复在改的地方；每条一句话，附文件路径或 commit
3. 照[盘问我](../grilling.md)一轮一轮问我：哪些方向想深挖、各挖多深，每题附你推荐的答案；事实你自己查，取舍等我答
4. 盘问结束、我确认之后，再按下面的写法讲，挑中的方向各多给一段

</div>

讲的时候：

- 三四段话，400 字以内；不分标题、不列清单、不画目录树、不贴命令
- 第一句纠正我原来的理解；没写就直接说它实际是什么
- 说清分工：哪些是程序做的，哪些留给人或模型
- 点出重心，用一个具体机制说明，不用形容词撑
- 技术词保留原形，其余用大白话
