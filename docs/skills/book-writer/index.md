# 别指望 AI 写得比官方文档好：调研仓库要先收窄到自己关心的那部分

在 deepseek-harness 和 SillyTavern 两个仓库上试过让 AI 先去打探、再写成手册。结论先说：

**AI 写不出比官方更好的文档手册。** 你有的 skill 官方开发者也有，他们还多了最了解代码的原作者。要通读一个仓库，第一站永远是官方文档。

**让 AI 探索仓库的意义在别处** —— 官方文档讲的是全貌，你要的往往是其中一小块的全部细节。先靠官方文档对整体有个印象，再派 AI 深挖自己感兴趣的部分，这才是它的位置。

## 派活的 prompt

下面是调研 SillyTavern 时真正用过的那条，原样照录（路径 `~/SillyTavern` 和 `@../zensical/docs/` 是当时那台机器上的位置，照抄要换成自己的）：

```text
我需要你非常仔细地调研本仓库（~/SillyTavern），整理出所有prompt工程的功能，先按大类（比如角色卡配置、世界书、用户配置、多人聊天）等等分大类，然后详细介绍里面的prompt工程能力，比如角色描述中可以拼接入 {{user}} 拼接用户名称，有生成推荐回复话术功能，可以控制上下文多少条截断，可以控制在哪一行（似乎是按照百分比？）插入世界书，世界书是按照条目区分，等等等等，每一个prompt工程的功能都能提升效果，所以也是我学习角色扮演agent搭建的重要知识点。 你可以用subagent来深入调研或者并行化加快速度。最终结果作为一篇大文章放在 @../zensical/docs/ 里面。每个大类可以用独立的子md，不必全部挤成一个文件

对了只关心 chat completion ,不用管 text completion模式

你必须严格看完所有代码，而不是直接找到现有的某些说明文档（可以作为参考）就停，要自己深入调研代码的所有功能

子代理写完之后的汇总结果你需要仔细详细检查（也可以是通过subagent来调查），看整体架构是否合理、子文章之间是否有冲突、是否都统一按照了mkdocs的规范（可以比md多一些提示等）
```

三个约束是这条 prompt 里真正起作用的部分：**限定范围**（只看 chat completion）、**禁止走捷径**（不许拿现成说明文档交差）、**要求自查**（汇总后检查子文章之间打不打架）。

## 先让 AI 预调研一遍，再定目标文档

直接开写会跑偏。正确顺序是先让它摸一遍仓库，产出一份带路径锚点的调研计划，人过一遍再放它去写：

- [SillyTavern 调研计划](reference/goal-st.md) —— 一次真实调研的完整执行规格：环境锚点、分几批派子代理、每批产出什么

## 没验证过的：loop 模式

看到别人用 AI 写书是另一套流程 —— loop 系统（我自己一直用的是 goal 模式），初稿写完再用 codex 生成一份改稿计划，内部做对抗式审计，力求跟原书风格一致。风格提示词大意是「面向新手、咖啡桌式讲解、生活比喻和实战案例的基本声线；同时依照出版改稿计划，把工作重点放在跨章节信息架构，而非机械删字或同义改写」。

**这套我没跑过**，记在这里是因为「先写完再对抗式改稿」的思路值得试，不是因为它被验证有效。
