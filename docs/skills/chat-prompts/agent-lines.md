# 指挥 Agent 的短句

在仓库里指挥 agent 时接在任务前后的短句。每句只给一个方向，不规定步骤 —— agent 自己能查上下文，缺的只是往哪想。按时机挑一句，点代码块右上角单独复制；【】里的换成自己的。

## 开工前

**整场讨论都不许迎合**，放在对话开头：

```text
请在与我的讨论和回答中遵循以下原则：以事实、证据和合理推理为依据，不因我的立场或偏好而迎合我，也不为反对而反对。如果我的观点、前提或推理存在问题，请直接指出并说明理由；依据不足或存在不确定性时，请明确说明，区分事实、推断与意见。表达应简洁、专业、重点突出，同时保留必要的解释和限定条件。
```

**需求还模糊，要先对齐再看几个方案**：

```text
先问一些不清晰的问题，对齐我的喜好，然后再出3版方案。
```

**怀疑自己把问题提错了**：

```text
不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来。
```

## 找解法

**修了几次都是补丁，要找到根上**：

```text
从第一性原理出发，找到最本质原因，修复一下。
```

**怀疑这个问题早就有名字、有成熟解法**：

```text
我的想法或目前存在的问题是否是其他领域经典问题的变体，有无成熟的解决方案，请进行跨领域的广度搜索核实这一点。
```

## 方案出来后

**只看了直接效果，要看连带影响**：

```text
不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。
```

**让它自己推翻自己的方案**：

```text
先假设你当前认为最合理的方案是错误的。站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况，至少列出 3 种，逐一做逆向压力测试。然后重新评估方案，看看有没有更好的解法。
```

**几个模型或几个 agent 对过答案，问它到底独立验证了什么**：

```text
如果其他几方都错了，你这次做的哪项独立核验，有机会发现那个错误。
```

## 聊偏了

**越聊越不对劲，要归拢一下**：

```text
请重新回顾此前围绕【讨论的主题】的设计讨论，独立重新评估该设计的取舍，并判断什么才是最佳方案；不要因为那些建议由我提出就倾向于接受，也不要为了迎合我而让步。给出你独立得出的推荐设计，说明理由、关键取舍和仍存在的不确定点或需要补充验证的信息。
```

## 整理项目

**找能删的历史包袱**：

```text
深入分析整个代码库的Git历史、关键PR和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
```

**看项目有多难懂**：

```text
假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。
```

**AI 留了一堆过程记录，要清掉**：

```text
请全面检查当前项目的所有文件（包括脚本、文档等），完成以下工作：逐项审查并确认代码结构干净、命名与结构统一归一、遵循单一职责原则；删除冗余内容、废弃的历史记录及历史思考过程，仅保留最终敲定的版本；最后对所有修改进行审核，并汇总说明发现的问题、已做的清理与调整，以及是否还存在潜在冗余或待确认的取舍。
```

**功能越加越散，要收拢**：

```text
从产品经理的角度去对整体功能需求进行收束，梳理一份核心功能架构，出一个mermaid的功能流程图。
```

**界面像说明书，要打磨到能交付**：

```text
从用户体验的视角，去对整体产品UI、UX设计做优化，去掉无用说明、改掉用户不懂的晦涩文字、最大程度简化用户操作，优化后使产品达到可交付的标准状态。
```

## 定期复盘

**同样的坑反复踩，要沉淀成机制**：

```text
全面复盘最近【多长时间】的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者Skill，避免我们反复支付同样的成本。能做成确定性检查（lint、类型、测试、脚本）的优先做成检查，不写成文字规则。
```
