# 上线体检

你现在是我的软件工程审查员。
请先阅读这个项目的实际代码和配置，再按照下面的清单逐项检查。

要求：

- 先判断每一项是否适用于我的产品。不适用的直接跳过，不要为了满足清单而增加无用的功能。
- 发现问题时，告诉我风险是什么、严重程度如何，并指出对应的代码文件或配置。不要只给通用建议。
- 没有实际检查到的地方，就说“无法确认”，不要假装检查过。
- 按严重程度排序，先告诉我最值得修复的10个问题，尤其是可能导致数据泄露、资金损失、服务中断的问题。
- 暂时不要修改代码。等我确认后，我们再一个一个解决。

以下是检查清单：

## 数据模型、登录与权限

- 有人设计过的表结构，而不是 AI 一张表一张表临场拼出来的
- 邮箱里带加号的人也能正常登录
- 重置密码的链接会过期，而且只能用一次
- MFA，外加给丢了手机的用户留一条找回的路
- 会话会超时，并且能让某个用户的所有会话一次下线
- SSO，给不支持就不签约的企业客户
- SAML，因为那家客户的 IT 部门不接受邮件魔法链接登录
- SCIM，员工被开除、IT 一办离职，他的权限当场收回
- 比「管理员」和「其他所有人」更细的角色和权限
- 校验，防止用户 A 改一下 URL 里的一个数字就读到用户 B 的数据
- 租户隔离，一个客户那边的 bug 永远不会把另一个客户的记录露出来
- 给客服用的「以该用户身份登录」管理员按钮，每次使用都留审计记录
- 登录限流，没人能大规模猜密码
- 账号锁定策略，能挡住攻击者，又不会在董事会前一晚把你们的 CFO 锁在门外

## 数据库

- 能向前执行、也能回滚的数据库迁移
- 不会在周二下午两点这种高峰时段锁住主表的迁移
- 索引 —— 测试时 50 行秒出的查询，到了 500 万行真实数据就会超时
- 连接池，一波流量高峰不会耗尽数据库连接
- 每晚备份
- 用这些备份真的恢复过一次 —— 没恢复过的备份只是一种希望
- 时间点恢复，应对有人跑了一条不带 where 的 delete 的那天
- 软删除，让「我不小心删了」只是一张客服工单，而不是一起事故

## 数据处理

- 服务端校验，不只是表单上校验
- 时区存对，早上 9 点的提醒不会在凌晨 4 点发出去
- 姓氏里带撇号的客户
- 每个字段都能处理 emoji、带重音的字母和从右往左书写的文字
- 金额用整数存，因为浮点数里 0.1 + 0.2 不等于 0.3
- 每个销售国家的币种、舍入和税务规则
- 扛得住第二个客户提出「就改一个小地方」的数据模型
- 幂等键，重试的支付请求不会把卡扣两次
- 去重，应对把提交按钮连点四次的用户
- 翻到第 400 页依然正常的分页
- 导出 —— 迟早每个客户都会要一份自己数据的表格
- 扛得住 2009 年某人存的那个 CSV 的导入
- 数据保留规则，以及真的去删合同里承诺要删的数据的代码

## 安全

- 密钥不在代码里、不在仓库里，也不在 AI 聊天记录里
- 轮换上个月 AI 粘进配置文件里的每一个 key
- 确认 AI 装的每个包都真实存在，而且就是你想要的那个
- 依赖扫描，因为 AI 引进了没人审过的库
- 用户能输入的每个地方都做输入清洗
- 防住 SQL 注入、XSS、CSRF，以及 OWASP 清单上的其余各项
- 上传的文件要扫描、限大小，并存在不能被执行的地方
- 不是「全部放行」的 CORS 规则
- 每个响应都带安全响应头
- 静态加密和传输加密
- 所有人都按最小权限，包括手握生产凭证的 AI agent
- 记录谁做了什么的日志，但不记密码、token 和卡号
- 在企业客户的安全团队自己动手之前，先做一次渗透测试
- 每个企业买家都会发来的安全问卷，每条答案背后都有证据
- 漏洞披露流程，应对某天一个陌生人发邮件告诉你有漏洞
- 一台能访问生产环境的笔记本被偷那天的应对预案

## 合规与审计

- SOC 2 —— 意味着制度、证据和审计师，不是勾一个框
- HIPAA —— 只要有一条病历进了你的系统就得管
- 和每个接触这些数据的供应商签 BAA，包括你的 AI 模型提供商
- 能看出谁查看过某条记录的审计记录，不只是谁改过
- PCI 范围，以及卡号不进你的数据库
- 能覆盖每张表、每份备份、每条日志的 GDPR 删除请求
- 数据驻留，给合同上写着「只能放在欧盟」的客户
- 有人签字确认的季度权限审查

## 环境与发布

- 互相一致的开发、预发布和生产环境
- 基础设施即代码，配置不只存在某一个人的脑子里
- 在任何东西到客户面前之前先跑测试的部署流水线
- 一键回滚，因为周五总会有人发版
- 零停机部署，因为你的客户没有维护窗口
- 功能开关，代码可以先上线，功能不必跟着上
- 自动扩容，扛住周一早上的高峰
- CDN，让应用在新加坡也加载得快
- DNS、SSL 证书，以及不会在周日过期的续期

## 后台任务、缓存与邮件

- 后台任务队列，慢活不会把页面卡死
- 带退避的重试，一次不稳的 API 调用不会变成一笔丢掉的订单
- 死信队列，接住重试全部失败的任务
- 加了第二台服务器那天不会跑两遍的定时任务
- 缓存，以及数据变了就清掉缓存
- SPF、DKIM 和 DMARC，重置密码的邮件不会进垃圾箱
- 每封事务邮件的退信和投诉处理

## 成本与容灾

- 存储规则，别再花钱留着 2021 年的临时文件
- 成本告警，失控的 agent 循环当天就能发现，而不是等账单来了才知道（原作者为这一条付过 1,382.59 美元）
- 写下来、每年演练一次的灾难恢复预案
- 第二个区域 —— 如果合同承诺的可用性单个区域给不了

## 监控与值班

- 凌晨三点也能搜的结构化日志
- 能把同一个 bug 归成一组的错误追踪，而不是给你发 4000 封邮件
- 从你自己网络之外发起的可用性检查
- 能呼叫到人的告警，调到不再为小事乱叫为止
- 延迟、错误率和吞吐量的仪表盘
- 链路追踪，一个慢请求经过的每个服务都能追到
- 值班轮换，以及真会接电话的人
- 运维手册，值班工程师知道「queue depth critical」是什么意思
- 真能带来改变的事故复盘
- 客户发邮件之前会先去看的状态页

## 测试

- 由懂这段逻辑该怎么跑的人写的单元测试
- 覆盖你依赖的每个第三方 API 的集成测试
- 覆盖注册、结账和其他赚钱流程的端到端测试
- 发上线公告邮件之前先做压测
- 像生产数据、但不是生产数据的测试数据
- 回归测试，修好第 41 号 bug 不会把第 12 号带回来
- 在你最大客户的运维团队还在用的那台五年前的笔记本上测试
- 无障碍合规，因为企业合同要求

## 计费

- 订阅、升级、降级和按比例计费
- 扣款失败的重试和催缴邮件
- 带客户采购单号的发票，因为没有它采购部门不付钱
- 销售税和增值税
- 退款、抵扣和部分退款
- 和账单一分不差的用量计量
- 带定制条款的年度合同 —— 计费逻辑从来没为它设计过
- 财务团队能对得上账的收入报表

## API 与第三方集成

- 校验签名的 webhook
- 会重试的 webhook，每次投递失败都有记录
- 有版本号的 API，改它不会弄坏客户的集成
- 客户能自己创建和吊销的 API key
- 既能保护你、又不挡住正常集成的 API 限流
- 第三方 API 不打招呼就改了返回格式那天的预案
- OAuth token 刷新，因为 token 总在最糟的时候过期
- 客户能测试集成的沙箱

## AI 功能

- 防提示词注入，每个会传到模型的字段都要防
- 客户和病人的数据不进会离开你们网络的 prompt
- 每个客户的模型花费上限，一个重度用户刷不爆你的账单
- evals，模型一更新、回答变差时你能发现
- 模型提供商宕机那个下午的备用方案
- 模型被弃用那天的迁移计划
- 用于调试的 prompt 和输出日志，去掉不允许保留的部分
- AI 做任何不可撤销的事之前，都要人工批准

## 界面与体验

- 在酒店 Wi-Fi 上也能打开的页面
- 每个界面都有空状态、加载状态和错误状态
- 客户看了知道怎么办的错误提示，而不是「出错了」
- 某个字段校验失败时，表单保留用户已经填的内容
- 在客户用的每种邮件客户端里都显示正常的邮件
- 用户可以关掉的通知
- 撤销
- 键盘导航和读屏支持
- 多语言翻译，日期和数字按各地区的格式显示
- 行为符合预期的返回按钮

## 代码与文档

- 人能读懂的代码
- 每次改动都有代码审查
- 分支策略，两个人同时干活不会互相覆盖
- 每月升级依赖，永远不落后两个大版本
- 在旧版本停止安全补丁之前升级框架
- 删掉 AI 前三次尝试留下的死代码
- 拆开 AI 一直往里追加的那个 2000 行的文件
- 写下来的架构决策，连同理由
- 让新工程师一小时内在本地跑起来的 README
- 给接手的人看的文档

## 运营与交接

- 给运营团队用的管理后台
- 客服工具，客户成功团队不用找工程师就能回答问题
- 客户看得懂的更新日志
- 和代码实际行为一致的服务条款和隐私政策
- 每个账号、域名和仓库都在公司名下，而不是在做原型的那个人名下
- 巴士系数大于一：没有哪个人一走，项目就停摆
