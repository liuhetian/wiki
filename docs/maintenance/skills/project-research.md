# 调研项目（project-research）

[调研项目](../../skills/project-research/index.md)的维护记录。[粗讲项目](../../skills/project-research/gist.md)、[细讲项目](../../skills/project-research/dissect.md)和[写书](../../skills/project-research/book.md)都是从本站对话里提炼的，没有外部上游。

- **单独成 skill**：两页原来是[对话提示词](../../skills/chat-prompts/index.md)「查证与研究」里的两段。2026-10-20 用户说「把本wiki中，skills中有如何调研项目，提到顶层来，AI调研写手册平级，我打算把写调研写手册skill退役掉」「而且放在 整理视频为笔记 之前，nav里顺序排在前面」。挪成顶层抽象 skill，两页各当一个迷你子 skill，正文不动，只改相对链接；两者的分工从对话提示词的入口挪到本 skill 的入口
- **AI 调研写手册退役**：同一天用户说「AI 调研写手册 直接删除，并且nav清理」。它讲的是让 AI 先探索仓库再写文档手册，附一份 SillyTavern 调研计划；调研仓库改用本 skill，SillyTavern 的成品在[项目拆解 · 酒馆 SillyTavern](../../projects/sillytavern/index.md)。内容没并进来，`redirects` 把两页的旧网址分别指到本 skill 入口和那篇拆解

## 粗讲项目 { #gist }

- **来源**：2026-10-19 让 AI 介绍 Rimagination/bili-note。第一版分目录、四层、演进讲，太细，用户说「就很粗地讲就好，不需要整理目录，就直接几句话讲」；第二版四段话，用户认可：「很好，就是想要这种总结」
- **怎么提炼的**：第二版成立靠读了源码 —— 用户以为它就是下载视频加转文本，代码里视频只在开关键帧时才下、转写是第三级兜底；取材那层代码最多，重心却在写前定篇幅。所以 prompt 要求先读源码，重心不按代码量判断。四段的骨架照第二版抽：先纠正原来的理解、说清程序和人的分工、点出重心配一个机制
- **探索选项**：用户随即要求加的：「对于大型项目，需要AI先探索项目，然后寻找里面的亮点或者更多读者都不知道有的部分，这需要一步一步讨论，需要参考 盘问我 这个skill」。加了一个默认「否」的选择，选「是」就先摸遍项目、列亮点，照[盘问我](../../skills/grilling.md)一轮轮挑方向，确认后再讲，挑中的方向各多给一段；同时按用户要求删掉「我和它的关系」那一栏
- **改成分支写法**：同一天复制按钮加了[分支](../../skills/wiki-guide/reference/branch.md)，这页当活例，用户说「可以在这个skill上试试效果吗，几种场景都试一试」。试的时候加过「在哪用」两支（能读文件的 agent / 网页对话框，网页那支末尾带一个 `required` 的多行框），用户看过源文件说「把这一个写作方案沉淀到本wiki的对应位置，然后还原成正式版本」，正式版去掉了它。留下的：「先探索」的开关包 `zx-no-copy` 只给人看，「否」也写一支「读完直接讲，不用先问我」，原来靠复制出去的「：否」传话；「我原来以为它是」填了才复制
- **删掉探索选项**：2026-10-20 细讲项目成型后，用户说「改为只保留简要收集，清理掉大型项目相关的」。要深挖大项目改用细讲项目，这页只管几句话讲清：「先探索」的开关和两支分支整段删掉，description 去掉对应半句；「读完直接讲，不用先把项目全摸一遍，也不用先问我」改成正文常驻；「我原来以为它是」填了才复制照旧。分支规范的活例换成细讲项目的「实跑」开关
- **引写作规范**：同一天用户说「要不加一行引用 wiki-guide/index.md 声明写作方式……不然我每次都还要复制」。粗讲讲给人听、不落成页面，只链文风一节，和本页「三四段、不列清单」冲突的按本页
- **纠正那句跟着填空走**：用户说「第一句纠正我原来的理解 这个不对，只有我写入了当前理解，才展示出来」。「第一句纠正」从「讲的时候」清单挪进「我原来以为它是」的 `data-when` 块，没填就整句不复制；「没写就直接说它实际是什么」删掉，AI 本来就这么讲
- **收纳开关**：用户说「对了写作风格这个引用，也需要加一个条件选择，用户选择是否要收纳到本wiki，默认是」，又说「讲完要不要收纳进本 wiki： 要完全隐藏，AI不会读，而且如果要收纳，要提醒AI看当前仓库，因为我肯定像现在一样在wiki这个工作区那执行的」。开关包 `zx-no-copy`，选「是」才复制收纳那句：点明当前工作区就是本 wiki 的仓库，先读仓库里的写作规范，引整篇不只引文风 —— 要收纳就得照整套流程落成页面；规范写成路径不写链接，复制按钮会把链接换成线上地址，AI 就跑去网上抓了。「否」不写块
- **默认骨架改成中性**：用户说「粗看项目这里，现在全部是学习设计，感觉这里应该做成一个下拉框呢，甚至大部分都不是在学习框架设计？」。bili-note 那次恰好挖到设计重心，「重心看设计花在哪、作者后来一直在补什么」就成了默认；粗讲更常见的用途是弄清一个链接是什么，学设计归细讲。默认改成它是什么、解决谁的什么问题、主路径怎么跑通、分工，「重心不按代码量判断」留下；加一个填了才复制的「我最想知道」。没做下拉框：用途之间只差侧重点，一句话就能让 AI 调整，选项要么太粗、要么越加越多，用户同意「好可以」
- **用过的**：bili-note 讲完没收纳；2026-10-20 粗讲 teableio/teable，收纳成[项目拆解 · Teable](../../projects/teable/index.md)，这是收纳开关第一次选「是」。项目拆解原来只有细讲的论文骨架，这次定下粗讲只放一页、commit 写脚注，规矩写在[项目拆解](../../projects/index.md)和写作规范的七问里
- **追问按问答补**：Teable 讲完用户追问「意思是给 postgres 加一层封装，就变成了一个google sheet？ 核心就是有了触发器之类的，能让某些列变成依赖其他列的函数？」，答完说「补充进去，不用考虑字数。 而且是以QA的形式来补充」。粗讲页正文后开「追问」一节，一问一个三级标题，问题照原话，不受三四段、400 字的限制；规矩写在[项目拆解](../../projects/index.md)

## 细讲项目 { #dissect }

- **来源**：2026-10-20 拆解 weidu12123/Liyuan（梨园），成品是[项目拆解 · 梨园](../../projects/liyuan/index.md)。先用粗讲项目的「先探索」读完、按设计重心写了六篇，用户换了角度：「首先它的领域算是什么？……最简单的做法就是网页chatgpt……一步一步是遇到了什么问题，所以引入xxx功能……只需要现状，不需要作者的心路历程」；改成功能线后用户说「你这样才是我看得懂的」
- **证据要真跑**：用户要求「每个部分拼接的时候，拼接模版，拼接效果展示出来，用真实的来距离，而不只是描述」，又说「两个字的中文关键词触发不了 这种小bug不需要忠实记录……我们要的是主线」。实跑最早是自己重写的模拟，收笔后还多调了一次模型，和梨园的真实行为对不上；改成直接 import 它的函数才对，所以 prompt 写死「不自己重写它的逻辑」
- **论文骨架**：用户问「感觉结构是不是越来越像一篇论文？」，又说「而且也是标题，摘要，关键词，背景，这样子的结构。我们能也仿照论文的结构吗？」「要不启动一个 细讲项目 的md, 来维护如何调研一个项目，用这种论文的方式」。照论文排：标题、摘要、关键词、背景、功能线（方法）、实验设置、可以搬走的设计（结论）、局限；文献综述和贡献声明是论文用来证明新颖的，拆解不需要，去掉；局限只写设计取舍，免得写成 bug 清单。「可以搬走的设计」是论文骨架补出来的，梨园那版原来没有
- **baseline 取自原来的理解**：粗讲项目的「我原来以为它是」一栏留了下来——这次用户以为梨园是「一个带上了一段system prompt的AI对话网页而已」，正好就是网页版 ChatGPT 这个 baseline，所以细讲里它不用纠正，直接当起点
- **字数**：粗讲的「三四段、400 字以内」不适用；入口 1500–3000 字、每条功能线 1000–2000 字，后者是用户先前定的「每个部分1000 —— 2000」
- **章节名照标准论文**：初稿把术语表放在关键词里、方法一节叫「功能线」，用户说「我觉得 功能线 这个不是标准论文里的模块呢？还有术语表在论文里也不该放在关键词这个部分吧」。改成引言、预备知识（术语表）、系统设计（按功能线分小节）、实验、局限、结论、附录；术语表加一栏出处，起因是用户问「一拍这种说法我从来没在别的地方见过呢？」——它是梨园自造的
- **实验设置进维护、功能线并进引言**：用户说「实验设置丢到维护手册里吧，我来学习项目不关心你的实验设计。 然后这个系统设计，要不直接作为引言？」。入口篇只剩摘要、关键词、术语、引言、局限、结论：功能线做引言的小节，因为入口篇相当于论文的前半部分，细讲篇才是正文各章；术语表挪到引言前，像工程论文的符号表
- **实跑开关给 AI 看**：开关原来包在 `zx-no-copy` 里只给人看，用户问「这个选择有什么价值呢？ 不需要加 zx-no-copy 吧，就是大大方方给AI看，事否需要实际跑项目」，改成正文里一句「关键机制要不要实际跑一遍：是 / 否」，复制时带上选的值；同时按用户说的加了「拆解关键片段来运行，不需要真的部署运行」
- **版本只记一次**：初稿要求「之后所有引用钉在它上面」，用户说「上面我觉得太严格了，在维护手册里面写一个当前参考的是哪个commit就足够了，我们又不是当历史学家做考据，抓住核心即可」，改成读的 commit 写进维护记录一次，正文不逐处标版本
- **引写作规范**：用户说「要不加一行引用 wiki-guide/index.md 声明写作方式……不然我每次都还要复制」，「写成什么样」开头加一句照写作规范写、本页没写到的按它来；复制按钮把站内链接换成绝对地址，AI 能顺着读到
- **收纳开关**：用户说「对了写作风格这个引用，也需要加一个条件选择，用户选择是否要收纳到本wiki，默认是」。和粗讲项目同一个开关、同样包 `zx-no-copy`，选「是」才复制「当前工作区就是本 wiki 的仓库，先读写作规范」那句
- **源码存档只存被引的**：2026-10-21 部署冒出 93 条构建警告，全出在 DeepSeek Harness、OpenAI Evals 的源码存档里。用户问「为什么存在这种压根没人看得到的内容」「我没让写过，怀疑是自作主张浪费token」。查下来，用户要的只是「拼接模版，拼接效果展示出来」，「先看许可再存档源码」是拆梨园时 AI 自己加进本页的；后两次拆解照着把上游设计文档整篇嵌进折叠块，又多拷了一批哪页都没引的文件。存档里的 `.md` 被 zensical 建成孤儿页、进了站内搜索，原文的相对链接指向没拷的文件，就成了警告。存档一条从「实跑」挪进「写成什么样」，改成只存被引到的、上游文档摘句加永链；`check-links.py` 加第 7 项，拦没人引的存档文件
- **没做的**：只在梨园上用过一次

## 写书 { #book }

- **来源**：2026-10-23 用户问「好像还有一个skill或者prompt，记录的如何写一个完整文档，类似一本书？」，指的是已退役的 AI 调研写手册；接着说「我想把调研分成几个阶段（虽然可以独立运行），粗调研、精细调查、写一本书」。把单个项目从头写到尾，写不过官方文档 —— 这是 AI 调研写手册自己的结论，也和细讲分不开。所以改成按读者读完能干什么分角度，「书只写官方文档没有的部分」放进备料第一步
- **角度给用户选、侧重单列**：用户说「从零复刻书 就用这个角度吧，从最简单的从0开始。 或者要不让用户来选择角度？……即便是从零搭建，可能也有侧重，比如有的项目关心内部功能，有的项目关心的是前端」。角度和侧重是正交的两件事：角度决定章节怎么排，做成下拉框，每个角度一支 `data-when`，各写自己的排法，没选中的那支长到值得省掉；侧重决定看哪一块，做成填了才复制的空，没填就从底稿里挑候选
- **收了三个角度**：用户说「领域书这个角度也很好。头脑风暴一下还有别的角度吗？」。头脑风暴出六个，收了从零复刻、领域对比、做实验（消融和反事实合成一个，都是动手量效果）。一条请求走到底、改造手册留作候选，等有项目要用再加；使用手册写不过官方文档，演化史和「只写现状」冲突，都不收
- **依赖做成底稿**：用户说「我们这三部曲，虽然独立使用，但是本质也是有依赖的，以来上一步的认识，关注点」。上一步的产出做成「底稿」填空：粗讲的「我原来以为它是」接细讲的 baseline，已有这条；细讲的 baseline、功能线、术语表、源码存档接写书。没给底稿，就照细讲的「先读」补个最小版；收纳时项目拆解里已有的就是底稿
- **写完通读挑错**：取自 AI 调研写手册里那条 SillyTavern prompt 的「汇总后检查子文章之间是否有冲突」，以及它末尾记着没验证过的「写完再对抗式改稿」
- **没做的**：还没写过一本；书放在 wiki 哪个板块没定，第一次收纳时盘问里问
