# 限制同时开工：完成一件，再拉一件

> 状态：待验证。

## 问题

看板上每件事都在“进行中”，不等于每件事都在推进。开工越多，切换、等待和重新进入上下文的成本越高；真正堵住的位置反而被一排半成品盖住。

## 做法

先把个人看板缩成三列：

```text
待开始 → 进行中 → 完成
          WIP = 1
```

**“进行中”最多只放一件主任务。** 只有它达到明确的完成条件，才能从“待开始”拉下一件。

实际工作不可能完全没有插单，可以加一条窄通道：

```text
主任务：WIP = 1
维护 / 紧急事项：WIP = 1
```

四条规矩：

1. **被阻塞的任务仍算 WIP** —— 不能移回待办来腾位置；先解除阻塞，或明确取消。
2. **完成条件先写清楚** —— “继续研究”永远完不成，“形成三条可比较方案”才能出列。
3. **到上限时先帮旧任务完成** —— 不用新开工制造“我很忙”的感觉。
4. **上限是实验值** —— 连续一周总被合理打破，再检查任务是否切得太大、流程是否真需要第二条通道。

团队使用时，WIP 限制应落在流程阶段，而不只是每个人头上。测试列塞满时，开发继续开新需求只会扩大堵点；正确动作是一起把测试列清掉。

## 为什么

Kanban 把 WIP 定义为某一时刻已经进入流程、尚未完成的工作。限制 WIP 会自然形成拉动：只有下游出现容量，上游才拉入新工作。

这条限制的价值不是让每个人保持满负荷，而是让工作稳定流过系统。空余容量不是浪费——它让人能处理阻塞、协助下游，并减少上下文切换。

## 先试一周

每天只记三项：

```text
今天开工数：
今天完成数：
最长卡住的一件事：
```

如果开工持续大于完成，先别提高 WIP 上限。找出是哪一步没有完成条件、外部等待没有负责人，或任务大到一周都出不了列。
